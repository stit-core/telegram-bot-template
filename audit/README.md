## TL;DR

**Это крепкий, дисциплинированный фундамент выше среднего — но сегодня он надёжен для «прочитать
кнопку → дёрнуть бэкенд → ответить», и НЕ надёжен для платежей и фоновых уведомлений в проде.**
Архитектура, типобезопасность, границы, тестовая гигиена и security-периметр — сильные (зелёный гейт,
84% покрытие, гексагон на машинном enforce, mypy strict настоящий, опасные места закрыты правильно).
Проблемы сконцентрированы в **надёжности доставки** и **сети восстановления ошибок** — и почти все
потери **тихие** (невидимы в телеметрии). Хорошая новость: **подавляющее большинство дефектов лежит в
`pylibinfra/tgbotkit`** (один-два прицельных PR), а не в архитектуре шаблона, и чинится **аддитивно**.

| | Оценка |
|---|---|
| Архитектура / границы / гексагон | **A−** (настоящий enforce, не косметика) |
| Качество кода / типы / гигиена | **A−** (strict, 0 техдолга в `src/bot`, 84% покрытие) |
| Гибкость / расширяемость | **B+** (5 из 6 путей роста открыты без правки kit) |
| **Надёжность доставки (платежи/уведомления)** | **D** (2 CRITICAL + платёжный HIGH, все с тихой потерей) |
| Готовность к realtime / мультибот / refund-recurring | **C−/D** (demo-уровень, нужны PR в kit) |
| Документация (вне скоупа — снесена намеренно) | n/a |

## Ответы на твои три вопроса

### 1. «Получится ли строить нормальных ботов?»

**Да — и довольно хороших, при двух условиях.** Каркас реально помогает писать *корректные* фичи:
конвенция форсится гейтом (import-linter + mypy strict + ruff), scaffold-скелеты точны, гексагон не
разваливается даже на большом флоу, типы не врут, security-периметр закрыт грамотно. Для типового
бота «команда/кнопка → диалог → вызов бэкенда → ответ» — это уже сейчас прочная основа.

Два условия:
- **(a)** до первого прод-бота с **платежами или фоновыми уведомлениями** нужно закрыть 2 CRITICAL и
  платёжный HIGH (фаза 0 роадмапа) — иначе будут тихие потери денег/сообщений. Это правки в `tgbotkit`,
  не переписывание шаблона.
- **(b)** ты — **не питонист**, а самый острый DX-обрыв сейчас — снесённая `docs/` (на которую
  ссылается всё ядро). Её восстановление (ты это и планируешь) критично именно для тебя: без неё
  кривая входа ведёт в пустоту.

### 2. «Насколько это гибкая система?»

**Гибкая правильной формы — на 5 из 6 проверенных путей роста расширяется БЕЗ правки kit:** добавить
фичу, добавить диалог/окно, сменить runner polling↔webhook (одна env-переменная), добавить язык,
выключить reference-фичу. Точки расширения (`RouterBundle`/`CommandBundle`/`NotifierBundle`/`ErrorUX`/
`OptionalLocaleResolver`/`OptionalStreamBus`) — образцовая dishka-идиома с last-wins override. Это
**сильная сторона**, подтверждённая эмпирически.

Где гибкость упирается — это **требовательные** сценарии (тяжёлый wizard с динамическими виджетами,
realtime fan-out, подписки/рефанды, мультитенант): шаблон как *референс* показывает простой happy-path
образцово, но требовательный кейс ты будешь проектировать сам по доке библиотеки или ждать PR в kit.
Это не тупик — это «непротянутые паттерны».

### 3. Тревога: «разные клиенты к разным API» — главное открытие аудита

**Твоя тревога обоснована по симптому, но сильно преувеличена по масштабу.** Да, в `platform/backend`
сейчас один `BackendClient` к одному API, и «из коробки» несколько типизированных клиентов не собрать
(dishka на двух провайдерах одного типа даёт тихий last-wins).

**НО** адверсариальная проверка эмпирически собрала **три** клиента с разными `base_url`/breaker'ами в
одном контейнере — это **~15–25 строк в самом шаблоне** по уже существующему в репо образцу
(`pgkit.ReplicaPool` через `NewType`-маркеры + `httpclient.Config(base_url=...)` напрямую). **PR в kit
не требуется.** Breaker изолирован per-`Client`; единственный остаточный минус — слипшиеся breaker-метрики
(косметика observability).

→ Это **не признак того, что «остальной код так себе».** Наоборот: аудит показал, что библиотека этот
паттерн уже умеет (`pgkit` им пользуется) — просто в HTTP-слой шаблона его не перенесли и не задокументировали.
Severity этой находки понижен с HIGH до **LOW**. Реальные риски системы лежат не здесь.

## Что нашли (по severity)

- **2 CRITICAL** (оба верифицированы, воспроизведены на коде):
  - **C1** — `RecoveryMiddleware` глотает dialog-ошибки раньше `dp.errors` → сеть восстановления UX мертва.
  - **C2** — тихая потеря фоновых уведомлений (at-most-once) из-за «mark-before-send + проглатывание + ack».
- **8 HIGH**: окно потери выдачи платежа; нет Telegram rate-limit; секреты голым `str`; мульти-тенант
  изолирует 1/8 стейта; realtime fan-out — демо-уровень; refund/recurring отсутствуют как класс;
  хрупкость на старте/разрыве инфры; poison-loop без `max_deliver`.
- **12 MEDIUM**: безлимитный рост state без TTL; `nc.drain` теряет таски; throttle режет фон;
  `pydantic.mypy` недонастроен; тесты дают ложный зелёный на критбагах; PII-redact дырявый; и др.
- **Сильные стороны** (S1–S8): зелёный тулчейн, настоящий гексагон, рантайм-ядро tgbotkit, честные типы,
  закрытый security-периметр, качественный httpclient, гибкость на 5/6 путей, prod-grade observability.

**Сквозные корни** (один фикс закрывает несколько находок):
1. «mark-before-commit + проглатывание» — **один корень → C2 + H1**.
2. Сеть восстановления дырявая ровно в момент сбоя; потери тихие.
3. «Построено впрок, не обкатано» — мёртвый конфиг и неподключённые киты.
4. Фоновый путь системно слабее основного (идёт мимо middleware).

## Методология (чтобы доверять цифрам)

- **Доказательность**: каждая находка — с `file:line`; многие воспроизведены эмпирически (живой
  `Dispatcher`, dishka-контейнер, прогон mypy/ruff/pytest/lint-imports на обоих репо).
- **Адверсариальность**: 9 топ-находок прошли проверку «опровергни по коду». Это **изменило выводы**:
  мульти-API понижен HIGH→LOW, rate-limit critical→HIGH, state-TTL и nats-drain HIGH→MEDIUM. Ни одна
  не опровергнута полностью, но severity откалиброваны честно.
- **Баланс**: сильные стороны фиксировались наравне с проблемами (раздел S1–S8).
- **Скоуп**: оба репо целиком (шаблон ~2.5k LOC + все 19 китов pylibinfra ~11.5k LOC). Намеренно
  снесённая `docs/` из находок исключена.
