# Аудит d-arch — целостность архитектуры и границ (сквозной синтез)

## Что смотрел

Это **синтез-линза**, а не поблочный разбор: читал поперёк обоих репо и поверх всех 18
готовых поблочных отчётов (`audit/raw/{t-*,k-*,p-*,_toolchain}.md`), сверяя их находки между
собой и достраивая то, что видно только в разрезе «через все компоненты».

Проверял лично (доказательно):

- **3 контракта import-linter** — прогнал `uv run lint-imports --config importlinter.toml`:
  **`Analyzed 87 files, 283 dependencies. Contracts: 3 kept, 0 broken.`** Все три держатся на
  реальном коде: «Слои внутри фичи (DIP)», «Независимость фич (cross-feature только через
  adapters/provider)», «Чистое ядро не импортит инфру».
- **Граница tgbotkit↔шаблон** — есть ли инфра-проводка в шаблоне / бизнес в ките (grep по
  `Bot`/`Dispatcher`/`RedisStorage`/`setup_dialogs`/`component`/`NewType` в `src/bot`).
- **Связность фич** — состав файлов каждой фичи, реальные cross-feature-импорты.
- **«Не городить велосипеды»** — нет ли локальных полукалек инфры в шаблоне.
- **Сквозные паттерны** — повторяющиеся через компоненты дефекты (мёртвый конфиг,
  mark-before-commit, переобещанные docstring'и).
- **«Построено впрок, не обкатано»** — реальные внешние потребители «китов про запас»
  (`config`/`flagkit`/`authnkit`/`bruteforcekit`/`auditkit`/`storagekit`).

## Сильные стороны (системные, видны только поперёк)

### 1. Заявленная архитектурная граница держится буквально и машинно

Это не декларация, а enforced-инвариант. Сошлись **независимо** все агенты по шаблону:
`Dispatcher`/`Bot`/`RedisStorage`/middleware/`setup_dialogs`/`setup_dishka` в `src/bot`
**отсутствуют** (k-tgbot-runtime §«Нет протечки aiogram»), composition root — только список
провайдеров (`app.py:29-59`, t-wiring), вся инфра-механика в ките. И обратно: бизнес-логика
(offer/policy/usecase) в `tgbotkit` отсутствует — kit параметризован (subject/durable/currency/
provider_token), а контент (`.ftl`, тексты) и маппинг живут в шаблоне (k-tgbot-feat, k-tgbot-i18n).
**Граница не односторонняя — она держится в обе стороны**, и это её главное достоинство: ни инфра
не течёт вниз, ни бизнес не всплывает вверх. import-linter форсит нижний слой этого на CI.

### 2. Гексагон согласован между фичами и градуирован по сложности

Поперёк 5 фич виден **единый и при этом гибкий** скелет (проверено составом файлов):

| фича | форма | файлы |
|---|---|---|
| `profile` | полный гексагон (эталон) | dto, errors, views, adapters, ports, policy, usecase, gateway, getters, handlers, dialogs, provider, state |
| `payments` | полный | (то же без adapters) |
| `start` | сокращённый | без dto/errors/views/adapters |
| `lang` | мини | policy/usecase/ports/provider + dialogs/handlers |
| `notifications` | вне гексагона | только `__init__`+`deliver` (NATS-router, не диалог) |

Это **не разнобой, а сознательная градация**: import-linter разрешает опциональные слои
(`importlinter.toml`), сокращённый гексагон официален (start/lang), а notifications корректно
вынесена из трёх контрактов (фоновый router — не вертикальный срез). Cross-feature сделан
образцово и однонаправленно: `profile→start` через порт `OnboardingReader`, объявленный
**в потребителе**, адаптер в `adapters.py`, связывание в `provider.py`; обратной зависимости нет
(t-feat-start-profile §2). Цикла нет by construction. Это редкая дисциплина — большинство кодовых
баз с «гексагоном на бумаге» сыпятся именно на cross-feature.

### 3. Единый dishka-паттерн «asymmetry» — консистентен по всей библиотеке

Сквозная находка p-cfg-time/t-wiring: **ни один кит не provide'ит свой `Config`** — его регистрирует
caller (`AppConfigProvider` собирает ВСЕ `*Config` в одном месте, `config.py:46-90`). Это повторяется
в logkit/cachekit/pgkit/natskit/config/flagkit одинаково, с перекрёстными комментариями-ссылками.
Один паттерн на 20 китов — это сильная архитектурная когерентность, и именно он даёт прямой
**контр-аргумент к тревоге заказчика** (см. ниже): kit намеренно не навязывает число инстансов.

### 4. Точки расширения — типизированные агрегаты + last-wins, а не магия

`RouterBundle`/`CommandBundle`/`NotifierBundle`/`ErrorUX`/`LocaleResolver`/`OptionalStreamBus` —
типы-агрегаты, которые kit отдаёт с дефолтами, а шаблон перекрывает одним `ExtensionProvider`
(k-tgbot-runtime, t-wiring проверил эмпирически: `Logger`≠nop, `RouterBundle`=4 роутера). Никаких
декораторов-с-глобальным-реестром, наследования или автодискавери. Шаблон **декларирует что**
подключить, а не **как**. Это правильная форма гибкости для ревьюабельного шаблона.

### 5. Принцип «не городить велосипеды» соблюдён — локальных полукалек инфры в шаблоне нет

Проверял специально: ни одного самодельного middleware/runner/storage/breaker в `src/bot`.
`platform/backend.BackendClient` — **не** велосипед, а тонкая anti-corruption-обёртка (≈2 вещи:
маппинг статусов + Idempotency-Key), вся транспорт-механика в `httpclient.Client` (t-platform,
p-http). `platform/webapp/init_data.py` НЕ дублирует HMAC-крипту — она в ките, шаблон только парсит
проверенное поле (t-platform). Это образцовое соблюдение директивы.

## Находки

### CRITICAL — СКВОЗНАЯ ТЕМА: «mark-before-commit + swallow» повторяется в 2 платёжно-критичных местах и в обоих теряет сообщение/выдачу

**CAT=correctness, CONF=high, KEY=yes**

Это **системный анти-паттерн**, а не локальный баг — и он самый опасный вывод аудита, потому что
проявляется через **три** независимых компонента одинаково, и каждый поблочный агент видел только
свою грань. Сквозной разрез (мои grep'ы + сведение k-tgbot-feat / p-msg / t-feat-payments /
t-feat-lang-notif):

Единственный примитив идемпотентности во всём ките — **`SET NX EX`, который метит ключ «seen» ДО
выполнения действия** (`tgbotkit/notifications/dedup.py:17`, `tgbotkit/payments/guard.py:24`,
`tgbotkit/middleware/dedup.py:34` — все три одной формы). А единственный примитив доставки —
**`Delivery.send_message`, который `except Exception` глотает** ошибку отправки
(`tgbotkit/notifications/delivery.py:40,50`). Сложение этих двух решений даёт детерминированную
потерю в двух бизнес-сценариях:

1. **Уведомления (CRITICAL у p-msg #1, HIGH у k-tgbot-feat):** `deliver.py:29` ставит dedup-seen →
   `send_message` падает (Telegram 5xx/flood-wait/бот заблокирован) → исключение проглочено →
   `JsBus._handle_one` видит «успех» → `msg.ack()` (`jetstream.py:144`). Сообщение потеряно, redelivery
   нет, а если бы был — dedup-ключ его отбросил. **At-most-once вопреки заявленному в доках
   at-least-once.**
2. **Платежи (HIGH у t-feat-payments):** `guard_charge` ставит `tg:charge:<id>` → `uc.complete`/
   `fulfill` падает при `BackendUnavailable` → исключение всплывает в recovery-middleware (глотается)
   → Telegram-redelivery `successful_payment` отбрасывается guard-ключом (стоит 7 дней). **Юзер
   оплатил звёздами, выдачи нет, авто-восстановления нет.**

Почему это **архитектурная**, а не точечная проблема: две половины кита держат **взаимоисключающие
контракты** — `Delivery` спроектирован «никогда не сигналить ошибку наверх» (чтобы не валить
consumer), а `JsBus`/`guard` спроектированы «отсутствие ошибки = commit». В стыке гарантия
рассыпается, и **примитив `seen()`/`guard_charge` физически не даёт построить безопасную доставку**:
у него нет reserve/commit-фазы. Это «недо-обобщённость одного примитива, протиражированная на все
точки его применения» (точная формулировка k-tgbot-feat).

**fix (системный, не пофайловый):** ввести в kit единый паттерн **reserve(key, short_ttl) →
commit(key, long_ttl)** вместо `seen()`/`guard_charge`-«поставил-и-забыл»; `Delivery` должен
возвращать признак доставки (или пробрасывать транзиентную ошибку → `nak`), commit ставить только
после успеха; добавить `max_deliver`+backoff на консьюмере (см. ниже). Это **один** PR в tgbotkit,
закрывающий обе бизнес-дыры разом — что и доказывает их общий корень.

### HIGH — СКВОЗНАЯ ТЕМА: «один бэкенд» зашит не в одном месте, а сквозной цепочкой типов — это главный архитектурный предел гибкости

**CAT=flexibility, CONF=high, KEY=yes**

Прямой ответ на тревогу заказчика, и она **обоснована** — но точнее, чем «синглтон». Свёл три
области (t-platform, p-http эмпирически, t-wiring):

- **Сам класс `httpclient.Client` НЕ синглтон** (p-http проверил: два `Client` с разными `base_url`
  имеют независимые breaker-фабрики и состояние). Самая страшная часть тревоги опровергнута.
- **Но «один бэкенд» зашит сквозной цепочкой type-keyed DI:** `HttpClientProvider` → один `Client`
  по типу → `BackendProvider` → один `BackendClient` по типу → все gateway просят `BackendClient`
  по типу (`profile/gateway.py:17`, `payments/gateway.py:17`). dishka резолвит по типу-ключу — второй
  типизированный клиент к другому API даёт коллизию ключа.
- **Подтверждено отсутствие путей расширения:** мой grep — `component`/`NewType` в `src/bot`
  **пусто** (изоляция графа dishka и именованные ключи нигде не применены); единый env-namespace
  `HTTPCLIENT_*` без префикса (p-http); единственный breaker-name `httpclient` (метрики сольются);
  гайд `scaffold/references/backend-port.md` знает только один backend.

Системный вывод: это **не «нельзя», а «не предусмотрено конвенцией»**. Для одного бэкенда — образцовая
anti-corruption-граница. Для нескольких API заказчику придётся либо городить второй слой
провайдеров/обёрток руками, либо это аддитивный PR в kit (`new_config(prefix=)` + `breaker_name`
в `Client` + фабрика именованных бэкендов).

**Важный нюанс для заказчика-непитониста:** библиотека-то это **умеет** — p-store показывает готовый
паттерн «несколько клиентов к разным бэкендам как отдельные DI-ключи» (`ReplicaPool` — отдельный pool
отдельным NewType-ключом, `pgkit/module.py:16,42`). То есть **единственность `BackendProvider` —
выбор шаблона, а не предел pylibinfra**. Сигнал «норм by design для one-backend, но точка
расширения под N не достроена», а не «архитектурный тупик».

**fix:** дать в шаблоне reference-паттерн именованных бэкендов (NewType-ключ на апстрим, как уже
сделано для реплики в pgkit) + параметризовать `httpclient.Config`/`breaker_name` env-префиксом в
ките; документировать в backend-port. INFRA-HANDOFF/PR в tgbotkit.

### HIGH — СКВОЗНАЯ ТЕМА: «построено впрок, не обкатано» — заметная доля инфры без единого потребителя, и часть этого кода — security-/secrets-критична

**CAT=architecture, CONF=high, KEY=yes**

Свёл p-cfg-time, p-sec, p-store + мой grep по внешним потребителям. Из 20 китов **значимая доля
никем не используется** ни в `pylibinfra`, ни в шаблоне:

| кит | внешних потребителей | риск «не обкатано» |
|---|---|---|
| `config` (loader+vault) | **0** | держит **секреты**: `load()` может поднять `ValidationError` со значением секрета в тексте; поля — голый `str`, не `SecretStr` (p-cfg-time medium) |
| `flagkit` | **0** | bool-парсинг молча роняет `yes/on/2`→False (тихий футган kill-switch) |
| `storagekit` | **0** | S3 `delete` никогда не кидает `ErrNotFound` — дрейф fake-vs-real (p-store) |
| `authnkit`/`bruteforcekit`/`auditkit` | не в `[tgbotkit]`, боту не нужны | `bruteforce.window` читается и **не делает ничего** (p-sec medium); audit «append-only» без триггеров |

Почему это **системная**, а не разрозненная тема: повторяется один и тот же риск-профиль —
**конфиг-параметр объявлен, валидируется тестом, читается из env, и ничего не делает**. Мой grep
подтвердил это как сквозной паттерн на 5 китах: `shutdown_drain` (tgbotkit), `window` (bruteforce),
`max_conn_lifetime` (pgkit), `write_timeout` (cachekit/httpkit), `state_ttl`/`data_ttl`/`max_deliver`
(вообще не объявлены, хотя нужны). Для заказчика-непитониста это **самый коварный класс**: «безопасный»
параметр выглядит настроенным, а защиты нет, и без чтения кода это не видно.

Чем грозит: (1) непротоптанные тропы — кто включит Vault-из-процесса или flagkit, наступит на
непокрытый-сценарием код («работает» = «проходит юнит на фейках», не «гоняли в проде»); (2) ложная
уверенность в «настроенной» защите (bruteforce-window, shutdown-drain); (3) утечка секрета в
трейсбек старта (config-слой без `SecretStr`). Само по себе наличие forward-provision — не порок
(building-blocks), порок — **молчаливое расхождение «конфиг обещает / код не делает»**.

**fix:** для каждого мёртвого параметра — либо реализовать, либо удалить поле+docstring (forward-only:
не держать обещаний, которых код не выполняет); для config-секретов — `SecretStr` + ловить
`ValidationError` без `input_value`; неподключённые киты (config/flagkit) — либо reference-wiring в
шаблоне с e2e-тестом, либо явная пометка «опциональная точка расширения, не обкатана».

### MEDIUM — НОВАЯ находка (видна только поперёк): тихий last-wins держится на нестрогой валидации dishka, а инфра-граница частично держится на «мёртвом коде по дизайну»

**CAT=architecture, CONF=high, KEY=no**

Свёл t-wiring (last-wins без `implicit_override`) + k-tgbot-mw (Recovery перехватывает dialog-ошибки
раньше `dp.errors`). Это **два проявления одного системного риска: корректность держится на порядке/
расположении, без машинной страховки.**

1. **Порядок провайдеров в `app.py` — единственный source of truth** корректности override'ов
   (Logger/RouterBundle/ErrorUX). dishka не в строгом режиме (`DEFAULT_VALIDATION`,
   `implicit_override=False`), поэтому случайная повторная регистрация типа пройдёт молча — победит
   последний (t-wiring medium). Рассинхрон двух списков фич (`app.py` Provider + `extensions.py`
   bundle) проявится не на сборке, а как «фича молча не реагирует» в рантайме.
2. **k-tgbot-mw находка #1 (critical в их области):** `RecoveryMiddleware` сидит **внутри**
   `ErrorsMiddleware`, поэтому `UnknownIntent/UnknownState` ловятся recovery раньше `dp.errors` →
   штатный stack-recovery aiogram_dialog и tailored stale-UX (`errorux.py`) — **мёртвый код для
   нормальных апдейтов**. То есть часть error-UX-границы существует, но никогда не исполняется из-за
   расположения в цепочке.

Системная связь: и тут, и там **заявленный инвариант держится на неявном порядке** (провайдеров /
middleware), а не на типах/тестах. Это хрупкая опора для «фундамента нормальных ботов»: одна
перестановка — и инвариант молча отвалится.

**fix:** (а) composition-smoke-тест, проверяющий что каждый зарегистрированный фиче-Provider имеет
роутер в bundle и что override'ы победили (Logger≠nop и т.п.) — ловит рассинхрон двух списков;
(б) `implicit_override=True` или явные `override=True` на перекрывающих провайдерах; (в) Recovery
должен пробрасывать `(UnknownIntent, OutdatedIntent, UnknownState)` наверх к `dp.errors` (правка в
ките).

### MEDIUM — СКВОЗНАЯ ТЕМА: фоновый путь (notifications) — системно недо-достроенная граница: не локализован, завязан на необъявленный контракт, не тестируется, без логов

**CAT=architecture, CONF=high, KEY=no**

Свёл t-feat-lang-notif + k-tgbot-feat + p-msg + p-testkit. По отдельности — четыре medium/low в разных
областях; **вместе — один системный вывод: фоновая доставка слабее остального бота по всем границам.**

- **Локаль:** `deliver.py:34` хардкодит русский текст; `Delivery.send_message` не имеет locale-пути,
  резолвер работает только на incoming-Update. Юзер с `en` получит push по-русски. Docstring
  переобещает «локаль закрыта в Delivery» — неверно (t-feat-lang-notif, k-tgbot-feat).
- **Идентификация:** доставка резолвит chat по `user_ref`, а пишется по `tg_id` — работает **только**
  если бэкенд кладёт в `user_ref` именно `tg_id`. Остальная архитектура идентифицирует юзера через
  `backend_user_id`. Реверс-карты нет → натуральный payload даст тихий промах (t-feat-lang-notif).
- **Наблюдаемость:** все ветки промаха `deliver.py` делают `return` **без единого лога** — массовая
  потеря push'ей будет невидимой (t-feat-lang-notif).
- **Тестируемость:** в testkit **нет** фейка `Delivery` с инъекцией ошибки — каждый бот пишет свой,
  и он никогда не падает; ветка «push упал → consumer выжил» непокрываема (p-testkit M1).

Системная причина одна: **фон идёт мимо middleware-цепочки** (нет request-контекста локали,
нет error-handler'а, нет observability-span с метрикой промаха), а точки расширения kit под фон
**недостаточны** (нет locale-хука в `Delivery`, нет reserve/commit-дедупа, нет фейка). Это не вина
шаблона — все 4 дыры лежат в граничном слое к kit, чинятся PR'ами в tgbotkit.

**fix:** locale-aware канал в `Delivery`; явный messaging-контракт на `user_ref` (или писать chat_link
по `backend_user_id`); `logkit.Logger` в `OrderDeliverer` с логом причины промаха; фейк `Delivery`
с `fail_on()` в testkit. Пакетом — это «достроить фоновую границу до уровня основной».

### LOW — НОВАЯ находка: tgbotkit type-check'ается под mypy 1.x (шаблон) и 2.x (kit) — общий API проверяется разными мажорами

**CAT=build, CONF=high, KEY=no**

Из _toolchain, но это **сквозной риск границы**: `telegram-bot-template/uv.lock` → mypy 1.20.2,
`pylibinfra/uv.lock` → mypy 2.1.0. Общий type-surface tgbotkit (по которому шаблон импортит kit)
валидируется **разными мажорами** (mypy 2.0 нёс ужесточения дефолтов). Зелёный mypy в ките не
гарантирует зелёный в шаблоне на том же коде. Для системы, где граница kit↔шаблон — центральный

## Ответ на вопросы заказчика (сквозной взгляд)

**1. Получится ли строить нормальных ботов?** **Да — это серьёзный, дисциплинированный фундамент
выше среднего.** Граница kit↔шаблон держится машинно (import-linter 3/3), гексагон согласован и
градуирован, observability/i18n/storage/middleware/runtime-ядро — production-grade (несколько агентов
независимо назвали runtime «самой сильной частью»). Кодовая гигиена образцовая (0 ignore/cast/print/
TODO в шаблоне, _toolchain). **Но** до прода есть **один системный блокер**: анти-паттерн
«mark-before-commit + swallow» теряет платёжные уведомления и платёжную выдачу при транзиентных сбоях
(CRITICAL). Он чинится **одним** концептуальным PR в kit (reserve/commit-дедуп), но без него «нормальный»
платёжный бот терять деньги пользователей будет молча.

**2. Насколько гибкая система?** **Гибкая правильной формы внутри парадигмы, негибкая на одной
конкретной оси.** Точки расширения (bundle'ы, Protocol-порты, ChainResolver, last-wins override,
asymmetry-конфиг) дают аддитивный рост без правки кита — это сильно. Цена гибкости: ручная регистрация
в двух списках без машинной страховки (medium), и **набор фич — код в composition root, а не конфиг**.
Единственная **реальная** ось негибкости — несколько типизированных клиентов к разным API (HIGH):
не предел библиотеки (pgkit показывает рабочий паттерн N-клиентов через NewType-ключи), а недостроенная
конвенция в шаблоне/httpclient. Отдельно: заметная доля инфры «построена впрок» (config/flagkit/sec-киты,
0 потребителей) — это «гибкость на бумаге», непротоптанные тропы.

**3. Один `BackendClient` — негибкость или норм by design?** **Гибридно, ближе к «норм by design для
one-backend + недостроенная точка расширения под N».** Для одного бэкенда — образцовая
anti-corruption-граница, не велосипед, не синглтон. Для нескольких API — реальная (не фатальная)
негибкость: «один бэкенд» зашит сквозной type-keyed цепочкой DI + единым env-namespace + единым
breaker-name + гайдом на один backend. **Ключевой контр-аргумент:** это выбор **шаблона**, а не предел
**библиотеки** — kit намеренно не provide'ит Config (asymmetry), а p-store демонстрирует готовый
паттерн «N клиентов = N DI-ключей». Заказчику с несколькими API нужен либо аккуратный самодельный
wiring (NewType-ключ на апстрim, как реплика в pgkit), либо аддитивный PR в kit — не переделка
архитектуры.
