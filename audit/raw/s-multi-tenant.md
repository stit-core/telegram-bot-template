# Стресс-тест: мультитенант / мультибот в одном деплое (id=s-multi-tenant)

**Сценарий.** Один деплой (один процесс) обслуживает **несколько ботов/тенантов**: разные
`BOT_TOKEN`, возможно разная конфигурация/локали/бэкенды per tenant; либо A/B-вариант. Пройти по
реальному коду: предполагает ли рантайм ровно один `Bot`/`Dispatcher`/токен; что мешает мультиботу
в одном процессе — изоляция состояния (Redis-namespace по `bot_id`), маршрутизация апдейтов,
webhook-роутинг по токену, общий ли контейнер.

**Вердикт сценария: BLOCKED** (для «несколько ботов в одном процессе»). Поддерживается лишь
вырожденный вариант — **несколько одинаковых инстансов одного бота** (горизонтальный скейл, общий
Redis): под него storage и isolation действительно подготовлены. Истинный мультитенант **в одном
процессе** архитектурой не предусмотрен и требует не правки шаблона, а переделки `BotProvider`/
рантайма в ките. Штатный путь под N тенантов — **N деплоев** (по процессу на токен), что k8s-нативно
и, вероятно, и есть by design — но это надо знать заранее, потому что часть кита (`with_bot_id`)
**намекает** на мультибот, которого на самом деле нет.

---

## Что смотрел

Прошёл весь путь жизненного цикла токена и стейта:

- **Рантайм-ядро (kit):** `module.py` (`BotProvider`: `bot`/`storage`/`dispatcher`/`runner`),
  `config.py` (env-поверхность, один `BOT_TOKEN`), `storage.py` (`build_storage`/`build_isolation`,
  `with_bot_id`), `runner/{base,polling,webhook}.py` (lifecycle, `set_webhook`, единственный
  `self._bot`).
- **Middleware-ключи (kit):** `middleware/dedup.py` (`tg:dedup:{bot_id}:{update_id}` — скоупится),
  `middleware/throttle.py` (`tg:throttle:{user.id}` — **НЕ** скоупится), `middleware/__init__.py`
  (порядок навешивания).
- **Не-FSM user-state (шаблон + kit):** `platform/links.py` (`link:tg:`/`onboard:tg:`/`link:chat:`
  — плоские ключи), `features/start/gateway.py` (`mark_onboarded`), `i18n/resolver.py`
  (`LocalePrefStore` → `locale:<user_id>`), `notifications/dedup.py` (`tg:notify:<key>`).
- **DI / composition root (шаблон):** `app.py` (`build_container` — один контейнер на процесс),
  `config.py` (`AppConfigProvider` — один `BotConfig`/`HttpConfig` на процесс), `extensions.py`
  (один `RouterBundle`/`Resolver`/`StreamBus`), `platform/backend/{provider,client.py}` (один
  `BackendClient` на один `httpclient.Config`).
- **Cache-слой (kit):** `cachekit/{config,cache,module}.py` — один `REDIS_URL`, один `db`, ключи
  пишутся **дословно**, без per-process namespace/prefix.

**Эмпирически проверил:**
- Изоляция FSM-ключей по `bot_id` реальна (`DefaultKeyBuilder(with_bot_id=True)`):
  `bot1 → fsm:111:10:20:default:data`, `bot2 → fsm:222:10:20:default:data` — расходятся. ✔
- Grep по обоим репо на `for … token`/`tokens`/`tenant`/`multi.*bot`/`Bot(` — **ни одного** цикла
  по токенам/тенантам; единственный `Bot(...)` — `module.py:79` из единственного `cfg.token`.

## Сильные стороны (под этот сценарий)

- **FSM/dialog-стейт честно изолирован по `bot_id`.** `storage.py:17` —
  `DefaultKeyBuilder(with_bot_id=True, with_destiny=True)`. Если когда-нибудь в одном Redis окажутся
  два бота (хоть из разных процессов), их FSM/dialog-контексты **не пересекутся** (проверено
  эмпирически). Это правильный задел под горизонтальный скейл и под общий Redis между деплоями.
- **`RedisEventIsolation` (`storage.py:21-22`)** даёт безопасность при ≥2 воркерах одного бота —
  два апдейта одного чата не войдут в гонку за контекст. Под «несколько инстансов одного токена»
  это закрывает главный риск.
- **Webhook-dedup скоупится `bot_id` (`dedup.py:33`)** — `tg:dedup:{bot_id}:{update_id}`. Даже на
  общем Redis два разных бота с совпавшим `update_id` не подавят апдейты друг друга. ✔ (Это и есть
  тот единственный ключ, где мультибот учтён осознанно.)
- **Контейнер собирается один раз и закрывается чисто** (`app.py:54-59`,
  `runner/base.py:76-81`) — под модель «один процесс = один тенант» (N деплоев) lifecycle корректен,
  никаких блокеров.

## Находки

### CRITICAL — Рантайм жёстко завязан на ОДИН `Bot`/`Dispatcher`/`token`: мультибот в одном процессе не выразим

**CAT=architecture, CONF=high, KEY=yes**

`BotProvider` (`module.py:38-133`) — APP-scope dishka-провайдер, который provide'ит **по одному**
экземпляру каждого:
- `bot` (`module.py:78-81`): `Bot(cfg.token, …)` — ровно один токен из единственного `cfg.token`
  (`config.py:30`). Нет коллекции ботов, нет фабрики `Bot` по токену.
- `dispatcher` (`module.py:88-110`): один `Dispatcher(storage=storage)` на процесс — он держит
  один набор роутеров/middleware/error-handlers.
- `runner` (`module.py:112-133`) → `build_runner` (`runner/__init__.py:21-42`): один runner с
  `self._bot`/`self._dp` (`runner/base.py:45-47`).

dishka различает зависимости по **типу**: тип `Bot` в графе ровно один, второй провайдер `Bot`
не «добавит второго бота», а перекроет первого (last-wins). То есть зарегистрировать N ботов в один
контейнер штатными средствами **нельзя** — нужен `WithParents`/тегирование/`alias` под N разных
типов, чего ни kit, ни шаблон не делают и под что не спроектированы.

Маршрутизации апдейтов между ботами тоже нет: `Dispatcher` один, `feed_update`/`start_polling`
принимают **тот самый** `self._bot` (`polling.py:13`, `webhook.py:28`). Нет диспетчера верхнего
уровня «по `bot.id` → нужный `Dispatcher`».

**Workaround:** нет (в рамках философии шаблона). Штатный путь — **N деплоев**: по процессу на
токен, у каждого свой `BOT_TOKEN`/`*_BASE_URL`/`BOT_I18N_*`. Это k8s-нативно, изоляция полная, и,
судя по `polling.py:3` («1 инстанс») и общему духу, **именно это и подразумевается**. Но кит сам
сеет двусмысленность (`with_bot_id=True`, см. ниже), будто мультибот-в-процессе поддержан.

### HIGH — `with_bot_id=True` обещает мультибот, которого нет: половинчатая изоляция (storage да, cache/throttle/links — нет)

**CAT=architecture, CONF=high, KEY=yes**

`storage.py:1-4` прямым текстом мотивирует `with_bot_id`: «key_builder с with_bot_id … **изолирует
мульти-бот**». Но изоляция по `bot_id` сделана **только** в FSM/dialog-сторадже и в webhook-dedup —
а весь остальной общий Redis-стейт пишется **плоскими ключами без `bot_id`**:

| Ключ | Где | Скоуп `bot_id`? |
|---|---|---|
| `fsm:{bot_id}:…` (FSM/dialog) | `storage.py:17` | ✔ да |
| `tg:dedup:{bot_id}:{update_id}` | `dedup.py:33` | ✔ да |
| `tg:throttle:{user.id}` | `throttle.py:26` | ✖ **нет** |
| `link:tg:{tg_id}` (backend-link) | `links.py:12,17` | ✖ **нет** |
| `onboard:tg:{tg_id}` (онбординг-флаг) | `links.py:13,21` | ✖ **нет** |
| `link:chat:{user_ref}` (чат для нотификаций) | `links.py:14,25` | ✖ **нет** |
| `locale:{user_id}` (преференс языка) | `i18n/resolver.py:36,42` | ✖ **нет** |
| `tg:notify:{key}` (delivery-dedup) | `notifications/dedup.py:17` | ✖ **нет** |

`cachekit.RedisCache` (`cache.py:34-59`) пишет ключи **дословно**, без per-процессного namespace, в
единственный `REDIS_URL`/`db` (`cachekit/config.py:8`). Значит если два бота когда-нибудь окажутся на
общем Redis (хоть это два деплоя на один инстанс Redis, что штатно), они **коллизят** по всему
не-FSM стейту: один и тот же `user.id`/`tg_id` у разных ботов — это **разные пользователи**, но они
делят `onboard:tg:`, `link:chat:`, `locale:`, `link:tg:`. Последствия конкретны:
- **онбординг тенанта A гасит онбординг у того же tg_id в боте B** (`onboard:tg:` общий) —
  пользователь B не пройдёт онбординг, т.к. флаг уже стоит от A;
- **`link:chat:` перетирается** — фоновое уведомление от бота A может уйти в чат, записанный ботом
  B (тот же `user_ref`), т.е. **cross-tenant доставка в чужой чат** (privacy-инцидент);
- **`link:tg:` (backend_user_id)** общий — identity бота A резолвит `backend_user_id`, записанный
  при линковке в боте B → апдейт уходит не в тот backend-аккаунт;
- **`locale:`** общий — смена языка в одном боте меняет язык того же tg_id в другом;
- **throttle** общий — юзеры разных ботов с одинаковым `user.id` делят token-bucket (это уже нашёл
  `k-tgbot-mw` находка 2).

То есть `with_bot_id=True` создаёт **ложное ощущение** мультибот-готовности: изолирована ровно одна
подсистема из восьми. Под реальный мультитенант (даже «N деплоев, общий Redis») это
**утечка/коллизия данных между тенантами**, а под «N деплоев, по Redis на тенант» —
`with_bot_id` вообще избыточен (в своём Redis бот один). Текущая половинчатость не работает ни под
один связный сценарий.

**Workaround (под общий Redis):** в шаблоне переписать `links.py`/`LocalePrefStore`-вызовы на
ключи с `bot.id`-префиксом — но `bot.id` доступен только асинхронно (`get_me`) и не прокинут в эти
call-site'ы; это уже не «правка формата ключа», а проброс bot-контекста через identity/usecase →
объёмная переделка. throttle/dedup-namespace — поверхность кита (PR). Чисто: либо документировать
«Redis на тенант обязателен» и убрать `with_bot_id`-обещание, либо честно скоупить **весь** стейт.

### HIGH — Конфигурация, бэкенды и локали — глобальные на процесс: per-tenant вариативность не выразима

**CAT=flexibility, CONF=high, KEY=yes**

Даже если отбросить «N ботов в процессе» и взять «N деплоев», часть сценария — *разная
конфигурация/локали/бэкенды per tenant* — упирается в то, что **всё конфигурируется один раз на
процесс**:

- **Один `BackendClient` на один `httpclient.Config`.** `BackendProvider` (`backend/provider.py:12-17`)
  даёт ровно один `BackendClient` поверх единственного `Client` (`HttpClientProvider`), а
  `HttpConfig` — один на процесс (`config.py:73-74`, из `HTTPCLIENT_*` env). Разные тенанты →
  разные backend-URL/креды **в одном процессе** невыразимы без второго провайдера с другим типом
  (это та же тревога заказчика про «несколько клиентов», подтверждённая `t-wiring`/`t-platform`).
- **Один набор локалей/Translator на процесс.** `install_i18n` (`module.py:103`) строит один
  `FluentTranslator` из `cfg.i18n.locales_dir` (`config.py:81-90`) — единый каталог `.ftl` на
  процесс. Per-tenant брендинг/набор локалей в одном процессе не задаётся.
- **Один `ChainResolver`/`StreamBus`/`RouterBundle`** (`extensions.py:37-60`) — одни роутеры, один
  резолвер локали, одна NATS-шина на процесс.
- **A/B-вариант:** нет механизма «выбрать вариант диалога/контента по флагу апдейта». Роутеры и
  контент фиксированы в `ExtensionProvider` на старте; ветвление можно сделать **внутри** getter'а
  руками, но это уже прикладной код, не точка расширения.

**Workaround:** per-tenant различие конфигов делается **на уровне деплоя** (разные env у разных
подов) — то есть N деплоев, по одному тенанту на процесс. Это рабочая и, вероятно, by-design модель,
но она означает, что «один деплой — несколько тенантов с разной конфигурацией» как поставлено в
сценарии — **не поддержано**; поддержано «несколько деплоев, по тенанту на каждый».

### MEDIUM — Webhook-роутинг рассчитан на один токен: один path, один secret, один `set_webhook`

**CAT=architecture, CONF=high, KEY=no**

`WebhookRunner._serve` (`webhook.py:31-51`) поднимает **один** POST-роут `cfg.webhook_path` с **одним**
`cfg.webhook_secret` и зовёт `self._bot.set_webhook(...)` для **единственного** бота. Telegram-нативный
способ мультибота на одном вебхук-сервере — путь вида `/tg/webhook/<token>` (роутинг по токену в
URL) + `feed_update` в нужный `Dispatcher` — **не реализован**: путь фиксированный (`config.py:41`),
бот один, секрет один. Под несколько ботов на одном webhook-ingress пришлось бы добавлять
token-в-path роутинг и мульти-`set_webhook` — это переделка `WebhookRunner` (PR в кит).

**Workaround:** N деплоев, у каждого свой `BOT_WEBHOOK_PATH`/`BOT_WEBHOOK_SECRET`/`BOT_TOKEN` и свой
ingress-роут. Работает, но это снова «процесс на тенант», не «деплой на N тенантов».

---

### LOW — `throttle`-ключ без `bot_id` (cross-bot token-bucket) — дубль находки k-tgbot-mw №2

**CAT=correctness, CONF=high, KEY=no**

`throttle.py:26` — `tg:throttle:{user.id}` без `bot_id`, в отличие от симметричного dedup
(`dedup.py:33`). На общем Redis юзеры разных ботов с одинаковым `user.id` делят token-bucket:
активность в боте A троттлит того же `user.id` в боте B. Уже зафиксировано `k-tgbot-mw` (находка 2);
здесь — как ещё один симптом негерметичности мультибот-изоляции. По дефолту `throttle_rps=0` (off),
поэтому LOW. **fix:** скоупить ключ `bot_id` (`tg:throttle:{bot_id}:{user.id}`).

---

### INFO — Per-process модель «один токен = один деплой» сама по себе разумна и масштабируема

**CAT=architecture, CONF=medium, KEY=no**

Чтобы не штрафовать by-design: «процесс на токен, скейл репликами одного токена» — это законная,
k8s-нативная и операционно простая модель (полная изоляция блейст-радиуса, отдельные секреты/квоты
per тенант, независимый деплой). Storage/isolation/dedup под неё подготовлены правильно. Проблема
не в выборе этой модели, а в том, что (а) кит её **нигде не декларирует** как инвариант, а (б)
наоборот сеет противоположный сигнал (`with_bot_id=True` + комментарий «изолирует мульти-бот»),
из-за чего потребитель может ошибочно решить, что общий Redis на N тенантов безопасен — и
напороться на коллизии из HIGH-находки. Это вопрос дисциплины/документации, а не механики.

  `runner/base.py:45-47` (`self._bot`/`self._dp`) :: workaround: нет в рамках одного процесса —

  `set_webhook(self._bot)` :: `runner/webhook.py:31-51`, `config.py:41-43` :: workaround: отдельный
  ingress/path/secret на каждый деплой.

## REQUIRED_CHANGES

Чтобы сценарий «несколько тенантов в одном процессе» стал **чистым** (всё — PR в `pylibinfra/tgbotkit`,
не правка шаблона; шаблон лишь подключал бы это):

1. **Мультибот в рантайме (кит).** Ввести понятие `BotId`/`tenant` первого класса:
   `BotProvider` отдаёт `dict[token → Bot]` / фабрику ботов; верхнеуровневый роутер апдейтов «по
   `bot.id` → нужный `Dispatcher`» (или один `Dispatcher` с bot-aware middleware); webhook
   token-в-path (`/tg/webhook/<token>`) + мульти-`set_webhook`. Это новая инфра-механика —
   архитектурный PR в кит, не косметика.
2. **Сквозной `bot_id`-namespace для ВСЕГО Redis-стейта (кит + шаблон).** Либо ввести в `cachekit`
   per-instance key-prefix (`Cache` с namespace), либо прокинуть `bot.id` во все call-site'ы:
   `throttle` (`bot_id`-скоуп симметрично dedup), `links.py`/`LocalePrefStore`/`notifications.dedup`
   — префикс `bot_id`. Без этого даже «N деплоев на общий Redis» небезопасно.
3. **Per-tenant конфиг/бэкенд/локали.** Разнести `httpclient.Config`/`Client`/`BackendClient` по
   тенант-тегам (несколько провайдеров с разными типами); per-tenant каталог локалей/Translator;
   per-tenant `RouterBundle`/`Resolver`. В шаблоне — выбор «по тенанту апдейта» в DI/getter'ах.

**Минимально (если мультитенант-в-процессе НЕ нужен — вероятный реальный случай):** документировать
инвариант «один процесс = один токен = один деплой; per-tenant различие — на уровне env разных
деплоев; общий Redis между тенантами НЕ поддержан». И **убрать ложный сигнал**: либо честно скоупить
весь стейт `bot_id`, либо снять обещание «with_bot_id изолирует мульти-бот» из `storage.py:1-4`,
оставив его как задел под «N инстансов одного токена / разные боты на физически разных Redis».

## Ответ на вопросы заказчика (в этой области)

**1. Получится ли строить нормальных ботов?** Да — для модели «один бот = один деплой» (со скейлом
репликами) всё на месте: FSM/dialog-стейт изолирован по `bot_id`, `RedisEventIsolation` закрывает
мультиворкер, webhook-dedup корректен, lifecycle чистый. Это нормальная и масштабируемая модель.
Чего **нет** — обслуживания нескольких ботов/тенантов **одним процессом**: рантайм жёстко на один

**2. Насколько гибкая система?** По оси мультитенантности — **жёсткая**: токен, бэкенд, локали,
роутеры, шина — всё единичное и на старте. Гибкость заложена под «разные деплои с разными env», не
под «один процесс — много вариантов». A/B/мультибренд в одном процессе потребует прикладного
ветвления внутри getter'ов или переделки точек расширения в кит. Опаснее то, что кит **намекает** на
мультибот (`with_bot_id`), но реализует его лишь на 1/8 стейта — это не гибкость, а ловушка:
потребитель поверит сигналу и получит cross-tenant коллизию.

**3. Про несколько клиентов к разным API.** Прямо релевантно сценарию: «несколько backend per
tenant» упирается ровно в ту же точку, что и тревога заказчика — один `BackendClient` на один
`httpclient.Config` на процесс (`backend/provider.py:12-17`, `config.py:73`). Со стороны *wiring* это
аддитивно (добавить провайдеры с другими типами, `t-wiring`/`t-platform` подтвердили), но «**per
tenant**, выбираемый по апдейту в одном процессе» — это уже мультитенант-механика, которой нет.
Симптом и тревога заказчика — одна и та же негибкость: всё, что должно бы варьироваться по тенанту,
сделано синглтоном на процесс.
