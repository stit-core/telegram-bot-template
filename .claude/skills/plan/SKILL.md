# Skill: plan

Планировщик. **Planning-first** — изменение идёт через план. План — это inline-секция в единственном артефакте `.claude/plans/roadmap.md`: `### <slug> — <title>` под `## Active`. Отдельных `<slug>.md`, подпапок и архивов нет — один файл, чтобы не расходиться с правдой.

План переживает `/clear` и перезапуск: он закоммичен, ревьюится в PR, читается заново в начале сессии. Пиши так, чтобы тебя-через-неделю продолжил с пол-оборота.

## Когда применять

- "/plan <задача>", "распиши план", "сначала запланируем", "давай спланируем".
- Любое **содержательное** изменение: новая фича/диалог-флоу, рефакторинг, новый порт/адаптер, новый middleware/job/notification, правка >1 файла, эволюция `StatesGroup`, подключение подсистемы.
- Требования размыты — план превращает разговор в письменный контракт.

## Когда НЕ применять

- **Truly-atomic** правка: опечатка, один очевидный файл, тривиальный one-liner. План дороже работы. Делай напрямую (но RED→GREEN по дефолту).
- **Багфикс — НИКОГДА не `plan`.** Любой фикс → skill `triage-failure` (строгая RED→GREEN петля). Исключение — research-spike, когда корневая причина неясна после ≥2 попыток: тогда план именно на spike, не на фикс.
- **Проектирование нового флоу диалога с нуля** (окна/переходы ещё не зафиксированы) — сначала `/dialog-deep-dive`, план — поверх его артефакта.
- Юзер уже дал готовый список шагов — запиши секцию без переспрашивания, но всё равно атомизируй и добавь Verify.

## Жизненный цикл

```
planning      — собираем контекст, задаём вопросы, пишем атомы
  ↓ approve
in-progress   — выполняем атомы, помечаем [x] + **Done:** evidence
  ↺ blocked   — упёрлись во внешнее/вопрос: Статус: blocked (blocked by: ...)
  ↓ все атомы зелёные
done          — ### -секция удаляется из roadmap (история в git log)
```

## Шаги

### 1. Понять задачу до записи плана

Спрашивай **до** записи — план на догадках хуже разговора. Минимум 3–5 релевантных вопросов из `references/questions.md` (скоуп / диалог-флоу / порты бэкенда / state-эволюция / cross-feature / i18n / тесты / rollout / инфра). Если на 5+ вопросов «не знаю / решай сам» — задача недозрелая: предложи research-spike или отложить.

Дизайн-вопросы не решай сам — спрашивай через `AskUserQuestion`.

### 2. Slug

`<verb>-<object>[-<qualifier>]`, kebab-case, 2–4 слова, без даты: `add-referral-feature`, `migrate-profile-states`, `add-order-notification`. Проверь, что секции `### <slug>` ещё нет в roadmap; коллизия → суффикс `-v2`.

### 3. Записать inline-секцию в `.claude/plans/roadmap.md` (под `## Active`)

Шаблон ниже. Подсекции — **bold-лейблы** (не `##`/`###`, они зарезервированы), фазы — `####`.

```markdown
### <slug> — <понятный заголовок>
**Создан:** <YYYY-MM-DD> · **Статус:** planning

**Контекст.** <2–5 предложений: зачем, что известно, что пробовали; ссылки file:line, коммиты.>

**Не входит в скоуп.** <что осознанно не делаем — дисциплинирует.>

**Открытые вопросы.**
- [x] Q1: <вопрос> → <ответ>
- [ ] Q2: <не закрыт — блокирует какие атомы?>

**Атомы.**

#### Phase 1 — <name>   (фазы — только для больших планов; мелкий — плоский список)
- [ ] **A1:** <короткое описание; ~1 коммит, ≤1 файл в среднем>
  - Verify: `make test` (или `uv run pytest tests/unit/test_X.py`) → PASS · Зависит от: —
- [ ] **A2:** <...>
  - Verify: `make check` → green · Зависит от: A1

**Infra impact.** — | <INFRA-HANDOFF-айтемы WHAT/WHY/ACTION/WHO/DECIDE/RISK; см. skill infra-handoff>

**Чекпоинты.**
- —
```

Стандарт атома:
- Ровно 1 коммит-worth работы; крупное — дроби.
- `Verify:` ОБЯЗАТЕЛЕН — конкретная `make`/`pytest`-команда + ожидаемый результат.
- `Зависит от:` ОБЯЗАТЕЛЕН (атом `A<N>` этой секции или `—`).
- По закрытии — под-буллет `- **Done:** <evidence>` (коммит-хеш / `make check → PASS` / `pytest → 3 passed`).
- Лимит ~15 атомов на план. Больше — разбей на 2+ зависимых плана (вторая `### `-секция с пометкой `(after <slug>)` в заголовке/контексте).

### 4. Стоп. Покажи план юзеру

Не начинай выполнение. Покажи: краткое резюме (3–5 строк), открытые вопросы, спроси «Approve и поехали? Или ещё подумать?». Юзер: approve / поправить / встречный вопрос / отложить.

### 5. Approve → in-progress

`**Статус:** planning` → `in-progress`. Обнови `**Current focus:**` в шапке roadmap. Дальше иди по атомам:
- `[ ]` → `[x]` + под-буллет `- **Done:** <evidence>`.
- Атом задел инфра-поверхность (env/секрет/webhook/NATS-subject/runtime-dep) → айтем в `**Infra impact.**` (skill `infra-handoff`).
- Атом меняет `StatesGroup` → веди по `state-migration` (deprecation вместо удаления).
- На границе фазы / каждые 3+ атома — чекпоинт (§6).

### 6. Чекпоинты

Триггеры: закрыто 3+ атома, новый открытый вопрос, план оказался неверным, юзер вернулся после паузы. Запись — **буллет** под `**Чекпоинты.**` (НЕ `### `):

```markdown
- **<YYYY-MM-DD> · <короткий заголовок>.**
  - Закрыто: A1, A2, A3 ✓
  - Обнаружено: <неочевидное>
  - Переоценил: A5 теперь блокирован Q3 → новый вопрос в Открытых
  - Следующий шаг: A4
```

### 7. Blocked

Упёрлись во внешнее (чужой PR, решение юзера, недоступный ресурс, нужен PR в `tgbotkit`) → `**Статус:** blocked (blocked by: <что>)`. Разблокировалось → вернуть `in-progress` + чекпоинт-запись.

### 8. DONE

Когда все атомы `[x]`:
1. **`**Infra impact.**` не пуст и не релизился?** Айтемы обязаны доехать до infra-стороны: либо `make release` их сагрегировал, либо перенеси строкой в `## Backlog`. Удалять план с несданным infra-impact нельзя.
2. Удали `### <slug>`-секцию целиком из `## Active`. История — в `git log`.
3. Разблокирован зависевший `(after <slug>)` план — отметь.
4. Незакрытый follow-up — отдельной строкой в `## Backlog` или новой `### `-секцией.
5. Обнови `**Current focus:**`. Сообщи юзеру: закрыто, секция удалена.

## Восстановление после /clear

1. Прочитай `.claude/plans/roadmap.md` — `**Current focus:**`, секции в `## Active`, их статусы.
2. В активной секции — последний чекпоинт, незакрытые атомы.
3. Сверься с `git log` с момента последнего чекпоинта — что план не отразил.
4. Расхождение → чекпоинт-запись. Продолжай со следующего открытого атома. Не перепланируй существующий in-progress план и не создавай параллельный.

## Что делает дотошно

- Спрашивает до записи; дизайн-решения — через `AskUserQuestion`, не угадывает.
- Атомы реально атомарны: «реализовать фичу» — это план, не атом. Дроби.
- У каждого атома Verify (`make`/`pytest`) и явная зависимость.
- «Не входит в скоуп» — отдельной подсекцией.
- Infra-impact заполняется сразу, не «потом» (доедет до release).

## Что НЕ делает

- ❌ Не пишет план без вопросов.
- ❌ Не правит код в фазе planning — только roadmap.md.
- ❌ Не заводит `<slug>.md`, подпапки, done/-архив — единый roadmap.
- ❌ Не использует `### `/`## ` внутри плана для подсекций/чекпоинтов — bold-лейблы и `#### ` для фаз.
- ❌ Не ведёт багфикс — это `triage-failure`.
- ❌ Не проектирует диалог-флоу с нуля внутри плана — это `dialog-deep-dive`.
- ❌ Не игнорирует активный план — продолжает его.
