# Skill: smartdev (cockpit)

Entry-point сессии бота: за один проход собрать состояние, поднять контекст и перейти в правильный
режим работы. Cockpit ведёт дальше: найденную проблему (красный гейт, infra-touch, правка состояний)
он не только называет, но и переключает в скилл, который её решает.

## Когда применять

- Начало сессии, после `/clear`, возврат после паузы.
- Юзер дал задачу, но непонятно, насколько она большая или в каком режиме её вести.

Узкая чёткая задача («поправь опечатку в X») идёт сразу в работу (RED→GREEN по умолчанию); в идущей
сессии с известным контекстом briefing не повторяй.

## 1. Состояние — `make status`

`scripts/status.sh` печатает секции `== Branch ==` (ветка, ahead/behind upstream, последний коммит),
`== Working tree ==`, `== Critical ==` (`SYNTAX`, `STACK-DRAFTS`), `== Infra-touch ==`
(незакоммиченные правки инфра-поверхности), `== Plan ==` (активные планы — статус, прогресс и
следующий шаг; число пунктов бэклога), `== Recent commits ==`, `== TODOs in changed files ==`.
Последняя строка — `OK` или `ATTENTION: <syntax|infra-touch …>`: это сигнал ветвления. Гейт
(ruff/import-linter/mypy/pytest) status не гоняет — его состояние знает только `make check`.

## 2. Контекст — читай файлы

Детект `make status` — сигнал ветвления, не вся картина. Ориентацию добери чтением:

- **Планы — `.claude/plans/`.** Активный план (`<slug> · in-progress · … · дальше: S<N> — …`) —
  прочти `.claude/plans/<slug>.md` целиком, начиная с «Где мы сейчас», и продолжай с него. Активных
  планов нет — предложи юзеру кандидатов «с чего начать» из `.claude/plans/backlog.md`.
- **Откуда задача.** Из корня проекта — от сессии корня или её фонового агента: задача или фаза
  программы хаба `<org>/infra`. Здесь она ведётся своим планом и обвязкой этого репо, а в хаб
  возвращаются тег образа (`/release`) и INFRA-HANDOFF. Прямой заход — та же обвязка.
- **Что это за бот** (свежая сессия) — `pyproject.toml` (`[project] name`, ревизия `pylibinfra` в
  `[tool.uv.sources]`), `docs/stack/` (что `draft`/`stable`), reference-фичи
  `start`/`profile`/`booking`/`payments`/`lang`/`notifications`: на месте и имя проекта ещё
  `telegram-bot-template` — форк не прошёл онбординг, путь — `/init-service`.
- **Источник дизайна** (задача про новый/изменённый флоу) — sibling `../strategy` (`<org>/strategy`)
  со слоем `telegram-bot-flow/<surface>/`: дизайн диалогов проектируется там, `/dialog-deep-dive` его
  транслирует. Есть стратегия — флоу идёт из неё (read-only), а не из интервью с нуля.
- Договорённости прошлых сессий живут в закоммиченных артефактах (планы с их «Где мы сейчас», CLAUDE.md,
  rules, `state/` deep-dive-скиллов); авто-память выключена (`autoMemoryEnabled: false`).

Контекст уже поднят в этой сессии — не перечитывай.

## 3. Переход в режим

Первый сработавший сигнал сверху вниз — переключайся туда и одной фразой скажи юзеру, куда и почему:

| Сигнал из status / задачи | Переход |
|---|---|
| `ATTENTION: syntax`, красный `make check` или тест (lint, mypy, import-linter, startup-smoke `emit_startup` — коллизия StatesGroup) | `triage-failure` (RED→GREEN разбор) |
| `ATTENTION: infra-touch` (правки `config.py`/`.env*`/`Dockerfile`/`compose.dev.yml`/`pyproject.toml`/notification-subject) | `infra-handoff` (INFRA-HANDOFF до claim/коммита) |
| Меняешь `State`/`StatesGroup` в `platform/dialogs/states.py` | `state-migration` (deprecation, не удаление живых State) |
| Активный план `in-progress` | следующий открытый атом; чекпоинты — по правилам `plan` |
| Задача = новый флоу диалога (окна/переходы ещё не зафиксированы) | `dialog-deep-dive`, затем `scaffold` |
| Задача содержательная (новый флоу/порт/подсистема, больше одного файла или слоя) | `plan` (декомпозиция и вопросы до кода) |
| Задача = добавить блок (feature/dialog/window/backend-port/middleware/job/notification) | `scaffold` (вариант по типу блока) |
| Багфикс любого размера | `triage-failure` (TDD, RED-first), не `plan` |
| Задача мелкая и понятная | прямо в работу по RED→GREEN (§4) |
| Нет задачи, нет плана, всё зелёно | спроси юзера, какую задачу решаем |

План в smartdev не пишется: переход в `plan` с задачей и собранным контекстом.

## 4. RED→GREEN→REFACTOR — петля по умолчанию

Любое изменение кода:

1. **RED** — сначала тест, выражающий желаемое/баг: `make test` или точечно
   `uv run pytest tests/unit/test_X.py` → red, и red по нужной причине.
2. **GREEN** — минимальный продакшен-код до зелёного.
3. **REFACTOR** — чистка при зелёном; `make test` держит зелёным.
4. Перед claim «готово» — `make check`.

Багфикс — строгий случай этой петли, его ведёт `triage-failure`. Отступление от RED→GREEN —
осознанное решение, проговори его юзеру.

## Briefing — read-only

Сводка и переход ничего не меняют: без правок и коммитов; `git pull`/`fetch` — только по просьбе
юзера; `make check` — перед claim «готово» или по просьбе, не в briefing. Активный план
продолжается со следующего атома, а не перепланируется.

## Формат вывода

Короткая сводка, которую читают за один взгляд: только то, что меняет следующий шаг, а не пересказ
вывода `make status`.

```
## Состояние
**Ветка:** `<branch>` <ahead/behind>
**Критичное:** syntax <OK|BROKEN> · stack-drafts <none|…>   (или ATTENTION: <…>)
**Infra-touch:** none / <файлы>
**План:** `<slug>` <статус> → дальше S<N>  (или —)

## Что висит
- <TODO / незакрытый handoff / draft stack-артефакт>

## Идеи в бэклоге (если активных планов нет)
- <кандидаты из `.claude/plans/backlog.md`>

## → Перехожу в <skill> / Продолжаю план с S<N>
<одна фраза почему>
```

Блок «Идеи в бэклоге» — только когда активного плана нет. Юзер дал задачу — после сводки сразу
§3 (оценка + переход) одним абзацем.
