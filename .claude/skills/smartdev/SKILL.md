# Skill: smartdev (cockpit)

Каноничный entry-point бота. Не «показать сводку и замолчать», а **вести**: за один проход собрать состояние, поднять контекст, и **самому переключить** в правильный режим работы. Если упёрлось в drift/красное/инфра — не описывай, а чейни в нужный skill.

## Когда применять

- Начало сессии, после `/clear`, возврат после паузы: "/smartdev", "что у нас", "с чего начать"
- Юзер дал задачу, но непонятно насколько большая
- Не уверен, какой режим сейчас правильный

## Когда НЕ применять

- Узкая чёткая задача ("поправь typo в X") — иди прямо в работу (RED→GREEN всё равно по дефолту)
- Уже идёт активная сессия с известным контекстом — не повторяй briefing

## Шаги

### 1. Собрать состояние

```bash
make status
```

Парси секции: ветка, working tree, drift/гейт (BUILD/`make check`-сигнал), infra-touch, активный план из roadmap. Последняя строка — `OK` или `ATTENTION:<что>`: это твой сигнал ветвления.

### 2. Поднять контекст (фикс «не помнит») — читай сам, не жди скрипта

`make status` даёт детерминированный **детект критичного** (red/drift/infra/ATTENTION) — это сигнал ветвления, не вся картина. Ориентацию по проекту добери **чтением файлов**:

- **Roadmap целиком — `.claude/plans/roadmap.md`.** Прочти `## Active` и `## Backlog` — отложенные идеи. Если Active пуст, **назови юзеру 1-3 backlog-пункта** как кандидатов «с чего начать».
- **Активный план** (`<slug>: in-progress | next: A#`) — прочти его inline-секцию: последний чекпоинт + следующий открытый атом. Продолжаешь с него, не с нуля.
- **Что это за бот** (свежая сессия / непонятно) — добери лениво: `pyproject.toml` (`[project] name`, `[tool.uv.sources]` ревизия pylibinfra → de-template'нутый форк или ещё канон-шаблон?), `docs/stack/` (стек, что `draft`/`stable`), наличие reference-фич `start`/`profile`/`payments`/`lang`/`notifications` (на месте → форк ещё «помнит» шаблон, путь — `/init-service`).
- **Источник дизайна** (если задача про новый/изменённый флоу) — рядом sibling-checkout'ом может лежать стратегия-репо (`<org>/strategy`, форк `business-strategy-template`) со слоем `telegram-bot-flow/<surface>/`: дизайн диалогов проектируется там, `/dialog-deep-dive` его транслирует. Есть стратегия → флоу идёт из неё (read-only), а не интервью с нуля.
- Договорённости прошлых сессий живут в закоммиченных артефактах (roadmap-чекпоинты, CLAUDE.md, rules, `state/` deep-dive-скиллов) — там сверяйся; авто-память в шаблоне не используется.

On-demand: контекст уже подняли в этой сессии — не перечитывай.

### 3. Чейнить (фикс «не ведёт дальше») — НЕ описывай, переключай

По приоритету сверху вниз. Первое сработавшее — переключаешься туда **сразу**, говоришь юзеру «→ перехожу в `<skill>`, потому что <причина>»:

| Сигнал из status / задачи | Действие — чейн |
|---|---|
| `ATTENTION:` red-тест / lint / mypy / import-linter / **`emit_startup`-smoke** (коллизия StatesGroup) | → `triage-failure` (RED-арм, RED→GREEN разбор) |
| Infra-touch не `none` (правишь `config.py`/`.env*`/`Dockerfile`/notification-subject/`pyproject.toml`-deps) | → `infra-handoff` (оформить INFRA-HANDOFF до claim/коммита) |
| Меняешь `State`/`StatesGroup` в `platform/dialogs/states.py` | → `state-migration` (deprecation, не удаление живых State; error-handler как сеть) |
| Активный план `in-progress` | Продолжай со следующего открытого атома; чекпоинт по правилам plan-skill |
| Задача = новый флоу диалога (окна/переходы ещё не зафиксированы) | → `dialog-deep-dive` (спроектировать флоу до кода), затем `scaffold` |
| Юзер дал задачу, big (меняет диалог-флоу/порт/подсистему, >5 шагов, >1 слой) | → `plan` (декомпозиция; planner спрашивает, не угадывает) |
| Задача = скаффолд (feature/dialog/window/backend-port/middleware/job/notification) | → `scaffold` (вариант по типу блока) |
| Багфикс (любого размера) | → `triage-failure` (TDD red-first; **не** `plan`) |
| Задача мелкая и понятная | Делай напрямую — но по RED→GREEN (см. §4) |
| Пусто (нет задачи, нет плана, всё зелёно) | Спроси юзера какую задачу решаем |

### 4. RED→GREEN→REFACTOR — дефолтная петля, не исключение

Любое изменение кода по умолчанию:

1. **RED** — сначала тест, выражающий желаемое/баг. Запусти `make test` (или точечно `uv run pytest tests/unit/test_X.py`) → убедись, что red, и red **по той причине**.
2. **GREEN** — минимальная правда продакшен-кода до зелёного.
3. **REFACTOR** — чистка при зелёном; `make test` держит зелёным.
4. Перед claim «готово» — `make check` (ruff + import-linter + mypy + pytest).

Багфикс — строгий случай этой петли, его ведёт `triage-failure`. Фича — та же петля, тест-first. Отступление от RED→GREEN — осознанное решение, проговори его юзеру.

### 5. Передача в planner

Нужен план — не делай его в smartdev. Чейнь в `plan` с задачей+контекстом. Planner — отдельная процедура с дотошными вопросами.

## Формат вывода

Сводка ≤25 строк + явный переход:

```
## Состояние
**Ветка:** `<branch>` <ahead/behind>
**Гейт:** check ok · import-linter ok · startup-smoke ok   (или ATTENTION:<...>)
**Infra-touch:** none / <файлы>
**План:** `<slug>` in-progress → next A#  (или —)

## Что висит
- <TODO / незакрытый infra-impact / draft stack-артефакт — max 3>

## Идеи в бэклоге (если Active пуст)
- <1-3 пункта из roadmap ## Backlog — кандидаты «с чего начать»>

## → Перехожу в <skill> / Продолжаю план с A#
<одна фраза почему>
```

Блок «Идеи в бэклоге» показывай, когда активного плана нет. Есть активный план — этот блок опускай. Если юзер дал задачу — после сводки сразу §3 (оценка+чейн) одним абзацем.

## Что smartdev НЕ делает

- Не гонит `make check` целиком сам (это перед claim «готово» / коммитом, или явная просьба).
- Не делает edits/коммитов в фазе briefing.
- Не `git pull`/`fetch` без явной просьбы.
- Не перепланирует активный план — продолжает его.

## Anti-patterns

- ❌ Дамп raw `make status` в чат. Сводка — резюме, не сырьё.
- ❌ Briefing на 100 строк. Юзер хочет картину за 30 секунд.
- ❌ Описать проблему и остановиться («есть коллизия StatesGroup»). Cockpit **переключает**, а не комментирует.
- ❌ Перепланировать вместо продолжения активного плана.
- ❌ Багфикс через `plan`. Багфикс → `triage-failure`, RED-first.
- ❌ Игнорить infra-touch или правку `states.py` (→ `state-migration`).
