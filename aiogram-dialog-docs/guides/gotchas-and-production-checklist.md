# Часть A — Подводные камни по темам

## Тема 1. Стек и состояние (task stack, Context, LaunchMode)

### 1.1. Лимит 100 диалогов на стек → `DialogStackOverflow`
- **Суть.** `Stack.push()` бросает `DialogStackOverflow`, когда в стеке уже
  `_STACK_LIMIT = 100` интентов. Каждый `start(mode=NORMAL)` без последующего
  `done()` добавляет новый `Context` в `intents` и НЕ освобождает память.
- **Чем грозит.** Повторный вход в одно и то же меню (например по `/start` без
  reset) копит контексты в storage, утекает память, и в какой-то момент бот падает
  на `DialogStackOverflow`. Контексты закрытых диалогов остаются, пока не вызван
  `done()`/`reset_stack()`.
- **Как избежать.** Для `/start` и «корневых» меню всегда используйте
  `StartMode.RESET_STACK` (см. 1.2) либо `LaunchMode.ROOT`/`LaunchMode.EXCLUSIVE`,
  которые чистят стек при старте. Не делайте рекурсивный `start` в `on_start` без
  условия выхода.
- **Главы:** 02 (§10.6), 04 (§11), 05 (§0, §12.1), 10 (§3.1, §7).

### 1.2. `/start` без `RESET_STACK` штабелирует диалоги
- **Суть.** Если `/start`-хендлер делает `manager.start(MainSG.main)` в режиме
  `NORMAL`, при каждом `/start` новый диалог кладётся ПОВЕРХ старого, стек растёт.
- **Чем грозит.** Тот же `DialogStackOverflow` (1.1) + пользователь возвращается не
  в чистое меню, а на старый стек.
- **Как избежать.** В `/start`-хендлере:
  `await manager.start(MainSG.main, mode=StartMode.RESET_STACK)` (в mega-примере
  ещё и `show_mode=ShowMode.SEND` для свежего сообщения). `RESET_STACK` вызывает
  `reset_stack(remove_keyboard=False)` — старые контексты стираются из storage.
- **Главы:** 01 (§10.9), 04 (§16.3), 05 (§12.1), 20 (§5.7, §10).

### 1.3. `LaunchMode.ROOT`/`EXCLUSIVE` сбрасывают стек МОЛЧА (без `on_close`)
- **Суть.** При старте диалога с `launch_mode in (ROOT, EXCLUSIVE)` менеджер делает
  `reset_stack(remove_keyboard=False)` ДО push — это удаляет все нижележащие
  контексты из storage без вызова их колбэков `on_close`/`on_process_result`.
- **Чем грозит.** Незакрытый прогресс/данные нижних диалогов теряются молча;
  колбэки-«хвосты» (например сохранение в БД в `on_close`) не отработают.
- **Как избежать.** Не кладите важный незавершённый прогресс под кнопку, ведущую в
  `ROOT`/`EXCLUSIVE`-диалог. Если нужны побочные эффекты при закрытии — закрывайте
  диалоги явным `done()`, а не полагайтесь на reset.
- **Главы:** 02 (§3, §10.10), 04 (§11), 05 (§4, §12.7).

### 1.4. Поверх `EXCLUSIVE`-диалога стартовать нельзя → `ValueError`
- **Суть.** `_start_normal` бросает `ValueError`, если верхний диалог в стеке —
  `LaunchMode.EXCLUSIVE`. **Текст ошибки врёт**: гласит
  `"Cannot start dialog on top of one with launch_mode==SINGLE"`, хотя проверяется
  `EXCLUSIVE` (см. также баг 14.1).
- **Чем грозит.** Кнопка `Start` на экране EXCLUSIVE-диалога уронит обработчик.
- **Как избежать.** Не размещайте `Start` в EXCLUSIVE-окнах; для перехода
  используйте `done()` (закрыть) либо новый стек (`StartMode.NEW_STACK`).
- **Главы:** 02 (§3, §10.6), 03 (§3), 05 (§2, §4).

### 1.5. `SINGLE_TOP` сравнивает диалоги по identity объекта
- **Суть.** `_process_launch_mode` для `SINGLE_TOP` снимает верхний контекст, только
  если `new_dialog is old_dialog` (тот же объект `Dialog`), а не по `StatesGroup`.
- **Чем грозит.** Если по ошибке создать два объекта `Dialog` для одной группы (что
  само по себе запрещено, см. 1.7) или ожидать замены «по смыслу» — поведение не то.
- **Как избежать.** Держите один объект `Dialog` на группу; полагайтесь на стандартный
  путь (один экземпляр диалога переиспользуется).
- **Главы:** 03 (§3), 05 (§4).

### 1.6. `dialog_manager` живёт ровно один апдейт; после хендлера он `disabled`
- **Суть.** `ManagerImpl` создаётся `ManagerMiddleware` на каждый апдейт; в `finally`
  вызывается `close_manager()`, который ставит `disabled = True` и обнуляет
  `_data`/`_event`. Почти любой метод после этого бросит `IncorrectBackgroundError`.
- **Чем грозит.** Сохранение `dialog_manager` в замыкание/фоновую задачу и обращение
  к нему позже → `IncorrectBackgroundError`. `dialog_data`/`current_context()` тоже
  падают.
- **Как избежать.** Для фона захватывайте только `chat_id`/`user_id`/`stack_id` и
  используйте `manager.bg(...)` или `manager.bg(...).fg()` (тема 11). Никогда не
  «протаскивайте» живой менеджер за пределы хендлера.
- **Главы:** 02 (§6, §10.1), 05 (§8), 06 (§1).

### 1.7. Одна `StatesGroup` = ровно один `Dialog`; коллизия всплывает поздно
- **Суть.** Две разные `Dialog` с одной `StatesGroup` → `ValueError("StatesGroup
  '<name>' is used in multiple dialogs ...")`. Ошибка бросается НЕ в `Dialog(...)` и
  НЕ в `include_router`, а в `registry.refresh()` — фактически на `emit_startup` или
  при первом обращении к реестру. `refresh` к тому же не идемпотентен (`_dialogs` не
  очищается перед сканированием).
- **Чем грозит.** Падение не на CI/тестах, а в проде при старте поллинга.
- **Как избежать.** В smoke-тесте гоняйте `await dp.emit_startup()` (или реальный
  старт), чтобы поймать коллизию на CI. Одна группа — один диалог.
- **Главы:** 01 (§4, §10.4), 04 (§15).

### 1.8. `switch_to` сам не перерисовывает; `next/back` не цикличны
- **Суть.** `switch_to` только меняет `context.state` (плюс `next/back` — обёртки над
  ним), но `show()` не вызывает — перерисовку обеспечивает поток обработки клика
  (`Dialog._callback_handler` → `_need_refresh` → `show`) или `update_handler` для
  bg. `next` на последнем окне и `back` на первом бросают `ValueError`.
- **Чем грозит.** В ручных/bg-сценариях после `switch_to` окно не обновится, если не
  вызвать `show()`. Динамический визард на краях упадёт `ValueError`.
- **Как избежать.** В ручных потоках после `switch_to` зовите `show()` сами. Для
  визардов проверяйте границы или используйте `switch_to` с явным целевым state.
  `switch_to` работает только внутри своей `StatesGroup` (иначе `ValueError` «Cannot
  switch to another state group») — между диалогами только `start`/`done`.
- **Главы:** 02 (§3, §10.4), 05 (§1, §12.2/12.3), 10 (§7).

### 1.9. `done()` на корне безопасен, но `on_process_result` не зовётся
- **Суть.** `Cancel`/`done()` на корневом (единственном) диалоге опустошает стек,
  убирает клавиатуру (`_remove_kbd`), `CONTEXT_KEY=None`. Родителя нет → его
  `on_process_result` не вызывается.
- **Чем грозит.** Логика возврата результата, повешенная на корневой `done`, молча не
  отработает.
- **Как избежать.** Не вешайте критичную возвратную логику на корневой `done`;
  результат имеет смысл только при наличии родителя.
- **Главы:** 05 (§3, §12.4), 10 (§2.4, §7).

### 1.10. `reset_stack`/`mark_closed` не вызывают колбэков
- **Суть.** `reset_stack` циклически `pop`+`remove_context` без `on_close`;
  `mark_closed` снимает контекст без `process_close`/`process_result`.
- **Чем грозит.** Побочные эффекты закрытия (БД, уведомления) пропускаются.
- **Как избежать.** Для корректного закрытия с колбэками и результатом используйте
  `done(result=...)`, а не `reset_stack`/`mark_closed`.
- **Главы:** 02 (§3, §10.10).

## Тема 2. Хранилище и сериализация (storage, persistence, миграции)

### 2.1. Только JSON-сериализуемое в `dialog_data`/`widget_data`/`start_data`/`result`
- **Суть.** Контракт типа — `Data = dict | list | int | str | float | None`. Всё это
  проходит `StorageProxy.save_context` → `storage.set_data` → backend aiogram. На
  JSON/Redis-backend `datetime`/`Decimal`/`set`/pydantic-модель/ORM-объект упадут
  `TypeError` ПРИ СОХРАНЕНИИ (то есть уже после ответа пользователю).
- **Чем грозит.** Краш в `context_saver_middleware` после хендлера; на pickle-backend
  «прокатит», но это анти-паттерн (непереносимо, ломается при смене классов).
- **Как избежать.** Кладите ISO-строки/числа/dict. `start_data` и `result` (включая
  тот, что уходит в `on_process_result` через bg-событие) — те же ограничения.
- **Главы:** 04 (§8, §16.1), 05 (§0, §12.5).

### 2.2. `MemoryStorage` не для прода
- **Суть.** Дефолтный из quickstart `MemoryStorage` хранит python-объекты в RAM:
  теряет все стеки/контексты при рестарте И маскирует ошибки сериализации (2.1).
- **Чем грозит.** После рестарта пользователи теряют открытые диалоги; кнопки старых
  сообщений становятся «протухшими»; ошибки несериализуемых данных вылезут только при
  переезде на персистентный storage.
- **Как избежать.** В проде — Redis/Mongo с JSON-сериализацией (не pickle). Для
  тестов берите `JsonMemoryStorage` из `test_tools` — он делает `json.dumps`/`loads`
  и ловит несериализуемые значения сразу.
- **Главы:** 01 (§10.8), 04 (§8, §16.2), 20 (§1.4).

### 2.3. Миграции `StatesGroup`/`State` ломают старые контексты
- **Суть.** `StorageProxy._state` восстанавливает `State` по строке. Удалённая/
  переименованная группа → `UnknownState`; удалённое состояние → тоже `UnknownState`;
  отсутствующий контекст → `UnknownIntent`.
- **Чем грозит.** После деплоя со сменой `StatesGroup` старые контексты в storage
  «битые». `IntentErrorMiddleware` сбросит битый стек (`_fix_broken_stack`) — но
  пользователь МОЛЧА потеряет открытый диалог.
- **Как избежать.** Планируйте совместимость состояний при деплое (не удаляйте/не
  переименовывайте группы и состояния без миграции). Обязательно повесьте
  error-handler на `UnknownIntent`/`UnknownState` (см. чеклист).
- **Главы:** 01 (§5.5), 04 (§5 `_state`, §7, §16.5).

### 2.4. `save_context` делает shallow-copy; часть полей `Stack` не сохраняется
- **Суть.** `save_context` = `copy(vars(context))` (поверхностная копия). А
  `save_stack` НЕ сохраняет `content_type`, `access_settings`,
  `has_protected_content` (они эфемерны/пересчитываются); `access_settings` стека
  всегда пересчитывается при загрузке через `_default_access_settings`.
- **Чем грозит.** Мутация тех же вложенных объектов между save и dumps — плохая идея.
  Рассчитывать на сохранение `access_settings` уровня стека нельзя.
- **Как избежать.** Не мутируйте `dialog_data`/`widget_data` после сохранения
  контекста в рамках одного апдейта; `access_settings` задавайте через `start(...)`.
- **Главы:** 04 (§5 save_context/save_stack, §8).

### 2.5. `remove_context`/`remove_stack` пишут `{}`, а не удаляют ключ
- **Суть.** Оба метода записывают пустой dict в ключ, не удаляя его из backend.
  `load_context` на такой ключ кинет `UnknownIntent`, `load_stack` вернёт пустой
  `Stack`.
- **Чем грозит.** В storage накапливаются пустые ключи (для некоторых backend это
  «мусор», который сам не подчищается).
- **Как избежать.** Имейте это в виду при аудите/очистке storage; при необходимости
  чистите пустые `aiogd:*`-ключи отдельной джобой.
- **Главы:** 04 (§5 remove_context/remove_stack).

## Тема 3. Масштабирование и многоинстансность

### 3.1. `events_isolation` по умолчанию in-memory (`SimpleEventIsolation`)
- **Суть.** Изоляция параллельной обработки апдейтов одного стека идёт через lock на
  ключ стека (`load_stack` берёт lock). Дефолт — `SimpleEventIsolation` (in-memory,
  per-process). Lock берётся на уровне стека: разные стеки параллельны, один стек —
  строго по очереди.
- **Чем грозит.** При нескольких воркерах/процессах in-memory lock не синхронизирует
  процессы → два процесса могут одновременно изменить один стек (гонка за `intents`/
  `dialog_data`, потеря записей).
- **Как избежать.** Для multi-worker передавайте распределённый isolation
  (`RedisEventIsolation` или свой) в `setup_dialogs(events_isolation=...)`.
- **Главы:** 01 (§10.10), 04 (§9, §16.4), 20 (§1.6).

### 3.2. `MediaIdStorage` (кеш file_id) — in-memory, per-process
- **Суть.** Дефолтный `MediaIdStorage` = `cachetools.LRUCache(maxsize=10240)` в
  памяти процесса. При нескольких воркерах/рестарте каждый прогревается заново.
- **Чем грозит.** Лишние первые аплоады файлов на каждый процесс/после рестарта
  (функционально безопасно, но лишний трафик/задержка).
- **Как избежать.** Если нужна общая экономия аплоадов — реализуйте
  `MediaIdStorageProtocol` поверх Redis/БД и передайте в
  `setup_dialogs(media_id_storage=...)`.
- **Главы:** 07 (§4, §8.14), 17 (§9).

### 3.3. Корень роутера обязан быть `Dispatcher` (для bg)
- **Суть.** `Updater.__init__` поднимается до корня и бросает
  `TypeError("Root router must be Dispatcher.")`, если `setup_dialogs` был вызван на
  изолированном `Router`, не включённом в `Dispatcher`.
- **Чем грозит.** Фоновые операции (`bg().start/update/...`, прогресс-бары) упадут.
- **Как избежать.** Включайте dialog-роутеры в `Dispatcher` ДО фоновых вызовов.
- **Главы:** 06 (§5, §12).

## Тема 4. callback_data и id виджетов

### 4.1. Лимит 64 байта на callback_data НЕ валидируется библиотекой
- **Суть.** Итог в проводе = `"<intent_id>\x1D<widget_id>[:<item>]"`. Telegram
  ограничивает callback_data 64 байтами (UTF-8). В `InlineKeyboardFactory` стоит
  `# TODO validate buttons` — проверки длины НЕТ.
- **Чем грозит.** Превышение всплывёт как ошибка Telegram API при ОТПРАВКЕ окна (не
  при сборке). Особенно опасны `Select`/`Radio`/`ListGroup`, где к `widget_id`
  добавляется `:item_id` (UUID, путь и т.п.).
- **Как избежать.** Короткие латинские `id`. Для длинных ключей храните маппинг и
  используйте короткий суррогатный id в `item_id_getter`.
- **Главы:** 09 (§7.2, §10.1), 10 (§4, §7), 11 (§11.2), 18 (§2.2, §10.7).

### 4.2. `id` валидируется регуляркой `^[a-zA-Z0-9_.]+$` в конструкторе
- **Суть.** `Actionable.__init__`: id из `[a-zA-Z0-9_.]`. Пробел, дефис, двоеточие,
  кириллица → `InvalidWidgetIdError` ещё на этапе конструирования (импорт модуля).
  Двоеточие исключено намеренно — это разделитель `_item_callback_data`.
- **Чем грозит.** Падение при импорте, а не в рантайме (хорошо), но неожиданно для
  тех, кто использует «человеческие» id.
- **Как избежать.** Только латиница/цифры/`_`/`.`. У `Button`/`Start`/`SwitchTo`/
  `TextInput`/stateful-виджетов id обязателен; у `Url`/`SwitchInlineQuery*`/
  `CopyText`/`Request*`/`MessageInput` — опционален или отсутствует.
- **Главы:** 09 (§3.1, §10.2), 10 (§4, §7), 11 (§8, §11.3), 12 (§5.6), 19 (§3, §14.2).

### 4.3. `id` обязан быть уникален в пределах диалога/окна
- **Суть.** `process_callback` матчит по точному `widget_id` или префиксу
  `widget_id:`. Два виджета с одинаковым id дают одинаковый callback_data → клик
  уйдёт первому по обходу, второй «мёртв». `find` тоже находит первый. Два stateful-
  виджета с одним id делят `widget_data` (затирают состояние друг друга).
- **Чем грозит.** Часть кнопок не работает; состояние Checkbox/Counter/Radio
  перемешивается. Особый риск: дефолтные id у `Next`/`Back`/`Cancel`
  (`__next__`/`__back__`/`__cancel__`) и у пейджеров (`__pager__`).
- **Как избежать.** Уникальные id в окне. Если в окне несколько `Next`/`Back`/
  `Cancel` с `on_click` — задавайте им явные разные id. Несколько пейджеров на один
  скролл — давайте явные id.
- **Главы:** 05 (§1 note), 09 (§7.3, §10.3), 10 (§7), 11 (§11.9), 12 (§5.6), 15
  (§3.1, §8.3).

### 4.4. Клик по «старой» кнопке прошлого контекста не сработает
- **Суть.** К callback_data добавляется `intent_id` текущего контекста. Если intent
  устарел (диалог закрыт/перекрыт), `_check_outdated` даст `OutdatedIntent`, и клик не
  обработается активным окном.
- **Чем грозит.** Это by design (защита от устаревших кнопок), но пользователь может
  «жать и ничего не происходит». `IntentErrorMiddleware` корректно гасит «часики» и
  при необходимости чинит стек.
- **Как избежать.** Поведение штатное; для корректного UX обновляйте/удаляйте старые
  сообщения. Не полагайтесь на клики по сообщениям из прошлых сессий.
- **Главы:** 04 (§4), 10 (§7).

## Тема 5. Рендеринг сообщений (ShowMode, edit/send/delete, MessageNotModified)

### 5.1. `ShowMode` одноразовый — действует на следующий show, потом AUTO
- **Суть.** Установленный `show_mode` влияет только на ближайший `show()`; затем фактически
  сбрасывается к AUTO (за счёт пересоздания менеджера на следующий апдейт).
- **Чем грозит.** Нельзя «залипить» режим между апдейтами через `manager.show_mode = ...`.
- **Как избежать.** Передавайте `show_mode` параметром нужного метода перехода
  (`manager.next(show_mode=...)`, `update(show_mode=...)`), а не глобально.
- **Главы:** 02 (§1, §4, §10.3), 05 (§5), 06 (§9).

### 5.2. Логика AUTO: почему на сообщение — SEND, на кнопку — EDIT
- **Суть.** `_calc_show_mode` для AUTO по порядку: не приватный чат → `EDIT`; была
  reply-клавиатура → `DELETE_AND_SEND`; не дефолтный стек → `EDIT`; событие `Message`
  без media_group → `SEND` (та же media_group → `EDIT`); иначе (callback/bg) → `EDIT`.
- **Чем грозит.** Сюрпризы: в группе/не-дефолтном стеке всегда `EDIT`; ответ
  пользователя в личке плодит НОВОЕ сообщение (`SEND`).
- **Как избежать.** Чтобы ответ пользователя не плодил сообщение — в `MessageInput`-
  хендлере ставьте `manager.show_mode = ShowMode.EDIT`. Понимайте, что для bg-событий
  AUTO почти всегда `EDIT`.
- **Главы:** 02 (§4), 05 (§5), 06 (§9), 07 (§5), 08 (§9 Progress), 20 (§7 FAQ).

### 5.3. EDIT — это НАМЕРЕНИЕ, а не гарантия (может уйти новое сообщение)
- **Суть.** `show_mode=EDIT`/AUTO фактически отправит НОВОЕ, если: нет старого
  сообщения (`old_message is None`, новый стек/потёрт `last_message_id`);
  редактирование невозможно (`_can_edit==False`: появилось/исчезло медиа, voice,
  reply-клавиатура); Telegram отказал («message can't be edited» / «to edit not
  found») → fallback на send.
- **Чем грозит.** Дубликаты сообщений там, где ожидалось «тихое» редактирование
  (особенно в фоне — `start()` логично создаёт новое сообщение).
- **Как избежать.** Если важно «никогда не плодить» — ловите случай удалённого
  пользователем сообщения и/или используйте `ShowMode.NO_UPDATE` там, где показ не
  нужен.
- **Главы:** 06 (§8, §9, §12), 07 (§3.2, §8.8).

### 5.4. `MessageNotModified` нельзя глушить
- **Суть.** На «message is not modified» и на `NO_UPDATE` менеджер бросает
  `MessageNotModified`; ядро ловит его в `show()` и НЕ сохраняет новые id — это
  нормальный поток, не ошибка.
- **Чем грозит.** Если в кастомном `show_message`/обёртке проглотить
  `MessageNotModified`, сломается логика «не сохранять id», возможны рассинхрон id и
  лишние перерисовки.
- **Как избежать.** В обёртках ретраите/глушите ТОЛЬКО сетевые/flood-ошибки
  (`TelegramRetryAfter`, `TelegramNetworkError`), а `MessageNotModified` пробрасывайте
  наверх.
- **Главы:** 07 (§1, §3.9, §8.1).

### 5.5. Reply-клавиатура → всегда delete+send, «мигание» чата
- **Суть.** Любое сообщение с `ReplyKeyboardMarkup`: `_can_edit==False` и
  `_message_changed` всегда `True` (клавиатуру нельзя сравнить) → всегда
  DELETE_AND_SEND/send. Снятие reply-клавиатуры стоит лишнего сообщения `"..."` +
  `ReplyKeyboardRemove`.
- **Чем грозит.** Чат «прыгает», новый `message_id` каждый показ, edit-оптимизации не
  работают, при переходе к окну без reply старые кнопки «залипают», если их не убрать.
- **Как избежать.** Reply-клавиатуру применяйте осознанно; при переходе к не-reply
  окну явно снимайте её. Для DELETE_AND_SEND порядок (send→delete при reply)
  оптимизирован, чтобы поле ввода не пропадало — сохраняйте его в кастомном
  `show_message`.
- **Главы:** 06 (§8), 07 (§3.4, §8.10, §8.13), 18 (§7, §10.6).

### 5.6. Удаление сообщений старше 48 ч недоступно
- **Суть.** Telegram не даёт удалять сообщения старше ~48 часов; для business-чатов
  `delete_message` недоступен вовсе (вместо удаления снимается клавиатура).
- **Чем грозит.** `DELETE_AND_SEND` для старого сообщения превратится в send без
  удаления → останется «хвост» (старое сообщение не подчистится). В business старые
  сообщения вообще не удаляются.
- **Как избежать.** Учитывайте «хвосты» в дизайне; для долгоживущих экранов не
  закладывайтесь на удаление. `remove_message_safe` глушит «to delete not found» и на
  «can't be deleted» снимает клавиатуру.
- **Главы:** 02 (§4), 05 (§5), 06 (§8, §9), 07 (§8.2, §8.3), 10 (§3.2).

### 5.7. `link_preview_options` всегда триггерит дифф (лишний edit)
- **Суть.** Если в `NewMessage` задан `link_preview_options` (даже идентичный
  прошлому), `_message_changed` возвращает `True` — будет лишнее редактирование.
- **Чем грозит.** Лишние edit-запросы в окнах, которые часто перерисовываются.
- **Как избежать.** Не задавайте `LinkPreview` без необходимости в часто
  перерисовываемых окнах. `LinkPreview` влияет только на текстовые сообщения
  (`send_text`/`edit_text`), у медиа этот параметр не используется.
- **Главы:** 07 (§3.3, §8.9), 17 (§7, §11.14).

## Тема 6. Медиа (StaticMedia, DynamicMedia, MediaScroll, кеш file_id)

### 6.1. Только один media-виджет на окно
- **Суть.** `ensure_media`: несколько `Media` → `ValueError("Only one media widget is
  supported")`. То же для `LinkPreview` («Only one link preview widget is supported»).
- **Чем грозит.** Падение при конструировании окна.
- **Как избежать.** Для выбора источника используйте `|` (`Or`) внутри ОДНОГО
  медиа-слота или `when`. Медиагруппы (альбомы) окном не поддерживаются — одно
  сообщение = одно вложение.
- **Главы:** 03 (§1.2, §9.3), 17 (§2, §8, §11.1, §11.11).

### 6.2. Кеш file_id по URL не инвалидируется
- **Суть.** `MediaIdStorage` кеширует по ключу `(path, url, type)`. Для `path` кеш
  инвалидируется по `mtime`; для `url` mtime = `None` → кеш БЕССРОЧНЫЙ.
- **Чем грозит.** Если содержимое по тому же URL изменилось, бот продолжит слать
  старый `file_id` (старую картинку).
- **Как избежать.** Меняйте URL/добавляйте version-параметр при смене контента, либо
  используйте `path` (mtime-инвалидация), либо `DynamicMedia` с явным `file_id`. Для
  `path` с одинаковым именем, но изменённым содержимым БЕЗ изменения mtime — кеш тоже
  отдаст старый file_id.
- **Главы:** 07 (§4, §8.11), 17 (§9, §11.4).

### 6.3. Редактирование медиа ограничено 5 типами; смена текст↔медиа = delete+send
- **Суть.** Отправка (`SEND_METHODS`) поддерживает 9 типов; редактирование
  (`INPUT_MEDIA_TYPES`) — только `ANIMATION/DOCUMENT/AUDIO/PHOTO/VIDEO`.
  `VIDEO_NOTE/STICKER/DICE` при попытке `edit_media` → `KeyError`. `VOICE` обходится
  принудительной переотправкой (`_can_edit` блокирует edit для voice). Появление/
  исчезновение медиа (текст↔медиа) → `_can_edit==False` → delete+send.
- **Чем грозит.** «Моргание» (новый message_id) при смене текст↔медиа; потенциальный
  `KeyError` при перерисовке VIDEO_NOTE/STICKER/DICE.
- **Как избежать.** Для VIDEO_NOTE/STICKER/DICE используйте `ShowMode.DELETE_AND_SEND`
  или окна без перерисовки. Не чередуйте текст и медиа в одном окне, если важна
  стабильность message_id.
- **Главы:** 07 (§3.1, §3.4, §8.4, §8.5), 17 (§3 ContentType, §11.9, §11.10).

### 6.4. Сравнение медиа идёт по `file_unique_id` — сохраняйте оба id
- **Суть.** `MediaId.__eq__`: если у одного `file_unique_id is None` → сравнение по
  `file_id`; иначе ТОЛЬКО по `file_unique_id` (Telegram даёт разные `file_id` для
  одного файла в разных чатах/типах, но `file_unique_id` стабилен).
- **Чем грозит.** Если кешируете/подставляете `MediaId` без `file_unique_id`,
  сравнение упадёт на нестабильный `file_id` → лишние перезаливы или ложное «не
  изменилось».
- **Как избежать.** Всегда сохраняйте оба id: `MediaId(file_id, file_unique_id)`.
- **Главы:** 07 (§2.4, §8.7), 17 (§3).

### 6.5. `DynamicMedia` selector синхронный; `itemgetter` кидает `KeyError`
- **Суть.** `DynamicMedia.selector(data)` вызывается БЕЗ `await` (async-селектор
  нельзя). Строковый selector = `itemgetter(key)` → `KeyError`, если ключа нет в
  `data`.
- **Чем грозит.** Падение рендера при отсутствии ключа; невозможность async-логики в
  селекторе.
- **Как избежать.** Всю async-работу (БД, S3) делайте в getter окна и кладите в `data`
  готовый `MediaAttachment`. Всегда кладите ключ (или плейсхолдер), либо используйте
  функцию-селектор, либо комбинируйте с `when`.
- **Главы:** 17 (§5, §11.7, §11.8).

### 6.6. Относительные пути в `StaticMedia(path=...)`
- **Суть.** `FSInputFile` резолвит путь относительно CWD процесса бота, а не модуля.
- **Чем грозит.** В проде (другой рабочий каталог) файл не найдётся.
- **Как избежать.** Используйте абсолютные пути (`os.path.join(BASE_DIR, ...)` /
  `pathlib`). `StaticMedia` не отдаёт `file_id` напрямую — для готового file_id нужен
  `DynamicMedia` + `MediaAttachment(file_id=MediaId(...))`.
- **Главы:** 17 (§4, §11.6, §11.16).

### 6.7. `MediaScroll` и пустой/укороченный список → `IndexError`
- **Суть.** `current_page = min(get_page, pages)`, но `items[pages]` при непустом
  списке = выход за границу (валидный максимум — `pages-1`); при пустом `items`
  (`pages=0`) `items[0]` → `IndexError`.
- **Чем грозит.** Падение рендера при удалении элементов без сброса страницы или при
  пустом списке.
- **Как избежать.** Сбрасывайте страницу при удалении элементов; оборачивайте
  `MediaScroll` в `when`, когда список может быть пуст.
- **Главы:** 17 (§6, §11.15).

## Тема 7. Ввод (MessageInput, TextInput, CombinedInput)

### 7.1. Ввод в неосновном стеке требует reply на сообщение с inline-кнопками
- **Суть.** Обычное сообщение грузит контекст ТОЛЬКО из `DEFAULT_STACK_ID`
  (`_load_default_context`). Диалог в дочернем/именованном стеке получит ввод, лишь
  если юзер ОТВЕТИТ (reply) на сообщение бота с inline-кнопками (intent берётся из
  reply через `_intent_id_from_reply`). Без inline-кнопок reply-механизм не работает
  (нет callback_data).
- **Чем грозит.** `MessageInput`/`TextInput` в окне неосновного стека «не работают»
  без reply — событие уходит в дефолтный контекст.
- **Как избежать.** Текстовый/медиа-ввод держите в дефолтном стеке; для неосновных
  стеков рассчитывайте на reply либо избегайте input-виджетов.
- **Главы:** 05 (§2 NEW_STACK), 14 (§9), 16 (§7.1), 20 (§6.3 multistack).

### 7.2. `TextInput` ловит ТОЛЬКО `ValueError`
- **Суть.** В `process_message` парсинг обёрнут в `except ValueError` → `on_error`.
  Любое другое исключение (`TypeError`, `KeyError`, `decimal.InvalidOperation`,
  `datetime.strptime` и т.п.) ПРОБРАСЫВАЕТСЯ в errors-роутер aiogram.
- **Чем грозит.** Кастомный парсер на `Decimal`/`datetime`, бросающий не-`ValueError`,
  уронит обработку вместо вызова `on_error`.
- **Как избежать.** В кастомных `type_factory` оборачивайте всё в `raise
  ValueError(...)`. `int("12.5")`/`float("1,5")` уже кидают `ValueError` — это ОК.
- **Главы:** 16 (§3, §7.2).

### 7.3. `TextInput` хранит исходную строку, не `T`; нет публичного `set_value`
- **Суть.** В `widget_data` сохраняется `message.text` (строка), а `get_value()`
  каждый раз ПЕРЕ-парсит её через `type_factory`. У `ManagedTextInput` есть только
  `get_value()` — НЕТ публичного `set_value()`/`clear()`.
- **Чем грозит.** Дорогой/недетерминированный `type_factory` гоняется на каждый
  `get_value`; нет штатного способа очистить/подставить значение.
- **Как избежать.** Дорогие парсеры кешируйте сами. Очистка:
  `manager.current_context().widget_data.pop("id", None)`. Ручная установка:
  `manager.find("id").set_widget_data(manager, "<строка>")` (передаётся СТРОКА, не
  `T`; метод унаследован от `Actionable`).
- **Главы:** 16 (§3, §7.3, §7.5).

### 7.4. catch-all `MessageInput` (ANY) только последним
- **Суть.** В окне один input-слот; ≥2 input → `CombinedInput`, где выигрывает ПЕРВЫЙ
  принявший (`process_message` вернул `True`). `MessageInput(content_types=ANY)`
  принимает всё.
- **Чем грозит.** Если catch-all поставить первым, он съест все сообщения, и
  `TextInput`/типизированные input после него никогда не сработают.
- **Как избежать.** Catch-all/fallback `MessageInput(ANY)` ставьте ПОСЛЕДНИМ. Идиома:
  `TextInput(...)` (отказывается от не-текста) первым, `MessageInput(fallback, ANY)`
  вторым — для фидбека «нужен текст».
- **Главы:** 14 (§8 MessageInput), 16 (§5, §7.6).

### 7.5. Прочие краевые случаи input
- **Суть/как избежать.**
  - Голый `Callable` в `Window(...)` становится `MessageInput`, НЕ getter (getter
    только через `getter=`). Это пересекается с темой 9/10.
  - `func=None` у `MessageInput` допустим — виджет «проглотит» сообщение нужного типа
    и вернёт `True`, ничего не сделав (заглушка-поглотитель).
  - `ContentType.ANY` в СПИСКЕ `content_types` отключает фильтр по типу целиком —
    остальные элементы списка игнорируются.
  - Альбомы (медиагруппы) приходят несколькими апдейтами — `MessageInput` сработает по
    разу на каждое фото (если нет album-middleware). Для фото берут `message.photo[-1]`.
  - После ввода окно перерисуется (`process_message` принявшего вернул `True` →
    `_need_refresh`); если переход уже сделан в коллбэке — повторного show не будет.
  - `CancelEventProcessing` из коллбэка → `processed=False` (тихая отмена перерисовки).
- **Главы:** 03 (§9.2), 14 (§8), 16 (§2, §5, §7.8/7.9/7.10/7.11/7.13).

## Тема 8. Reply-клавиатура и scope (Request-кнопки, ReplyKeyboardFactory, ForceReply)

### 8.1. Reply-клавиатура запрещена вне `DEFAULT_STACK_ID` → `InvalidKeyboardType`
- **Суть.** `_ensure_stack_compatible`: `ReplyKeyboardMarkup` в не-дефолтном стеке →
  `InvalidKeyboardType`. Причина: reply-клавиатура принадлежит чату целиком, а не
  сообщению; несколько стеков с reply конфликтовали бы.
- **Чем грозит.** Окно с `ReplyKeyboardFactory`, запущенное в `bg`/отдельном стеке,
  уронит показ.
- **Как избежать.** Не используйте `ReplyKeyboardFactory` в окнах, которые могут
  запускаться в дополнительном стеке. `InlineKeyboardMarkup`/`ForceReply` ограничений
  по стеку не имеют.
- **Главы:** 02 (§3, §10.7), 04 (§10), 07 (§5), 18 (§8, §10.5).

### 8.2. `callback.answer()` падает в reply-окне → `ValueError`
- **Суть.** Reply-кнопки не дают настоящий `callback_query`; библиотека эмулирует его
  через `ReplyCallbackQuery`, чей `.answer()` бросает `ValueError` («Support of
  `.answer()` call is impossible»).
- **Чем грозит.** Универсальный `on_click`, вызывающий `callback.answer()` (тост/
  алерт), сломается, если виджет окажется в reply-режиме.
- **Как избежать.** Не вызывайте `.answer()` в shared-виджетах, которые могут попасть
  в reply-окно; проверяйте тип события. Для обычных inline-кнопок «часики» гасятся
  автоматически (`dialog_manager.answer_callback()`), `callback.answer()` руками не
  нужен.
- **Главы:** 09 (§6), 18 (§6.3, §10.2).

### 8.3. Request-кнопки: нет callback, результат — отдельным сообщением
- **Суть.** Реально есть только `RequestContact`/`RequestLocation`/`RequestPoll` (это
  `KeyboardButton`, не inline). У них НЕТ `on_click`, НЕТ `widget_id`
  (`manager.find` не найдёт), `process_callback` всегда `False`. Результат приходит
  обычным `Message` (`message.contact`/`location`/`poll`). `add_intent_id` к
  `KeyboardButton` не применяется → intent к Request-кнопке не привязан.
- **Чем грозит.** Ожидание `on_click`/`find` не оправдается; результат корректно
  доезжает преимущественно в ДЕФОЛТНОМ стеке (см. 7.1) — в кастомных стеках хрупко.
- **Как избежать.** Ловите результат через `MessageInput(content_types=CONTACT/
  LOCATION/POLL)` или `on_message`. Используйте только с
  `markup_factory=ReplyKeyboardFactory()` (дефолт окна — inline). `RequestUser/
  RequestUsers/RequestChat` в библиотеке НЕТ — делайте подклассом `Keyboard` вручную.
- **Главы:** 14 (§TL;DR, §8, §9, §11, §12).

### 8.4. `Url`/`SwitchInlineQuery`/`CopyText`/`LoginURL` в reply-окне → `ValueError`
- **Суть.** `transform_to_reply_keyboard`: inline-кнопка без `callback_data` и без
  `web_app` (url, switch_inline_query, copy_text, login_url, pay) не конвертируется в
  reply → `ValueError`.
- **Чем грозит.** Падение рендера окна с `ReplyKeyboardFactory`, если в нём есть такие
  кнопки.
- **Как избежать.** В reply-окнах не используйте `Url`/`SwitchInlineQuery*`/`CopyText`/
  `LoginURLButton`. `WebApp`-кнопка конвертируется (web_app сохраняется).
- **Главы:** 18 (§3.2, §9, §10.4).

### 8.5. `ForceReplyFactory` игнорирует клавиатуру; `input_field_placeholder` — TextWidget
- **Суть.** `ForceReplyFactory` полностью игнорирует `keyboard` — кнопки в окне не
  отрисуются, их `on_click` недостижим. `input_field_placeholder` (в Reply и Force) —
  это `TextWidget`, не `str`.
- **Чем грозит.** Невидимые кнопки в ForceReply-окне; передача строки в placeholder
  (`"text"`) — у строки нет `render_text` → ошибка.
- **Как избежать.** В ForceReply-окнах обрабатывайте ответ через `MessageInput`.
  Placeholder задавайте через `Const("...")`/`Format("...")`.
- **Главы:** 14 (§7, §10), 18 (§4, §10.3, §10.8).

## Тема 9. Виджеты с состоянием (Checkbox, Counter, Select, Radio, Multiselect, Toggle)

### 9.1. `default` «прилипает» через `setdefault` после первого чтения
- **Суть.** `get_widget_data` использует `dict.setdefault`: при ПЕРВОМ обращении
  (рендер/`find().is_checked()`/`get_value()`) default записывается в `widget_data` и
  дальше не влияет. Состояние живёт в контексте до закрытия диалога.
- **Чем грозит.** Менять `default=` в коде для уже открытого диалога бесполезно —
  состояние зафиксировано. Сбрасывается только пересозданием контекста (новый старт/
  `RESET_STACK`).
- **Как избежать.** Предзаполнение делайте в `on_start` диалога через
  `set_checked(...)`/`set_value(...)`, а не через `default` после открытия.
- **Главы:** 11 (§11.4 min_selected), 12 (§0, §5.1), 19 (§3).

### 9.2. `Counter` молча игнорирует выход за границы и работает в `float`
- **Суть.** `set_value` НЕ клампит и не бросает: если значение вне `[min, max]` —
  просто ничего не делает, `on_value_changed` не зовётся. `increment`, не делящий
  диапазон, «застревает» у границы. Тип значения — `float` (`5.0` вместо `5`).
- **Чем грозит.** Программный `set_value(9999999)` при max=10 — тихий no-op; клик «+»
  у границы без `cycle` оставляет старое значение; float-погрешность при дробном
  increment; `==`-сравнения ненадёжны.
- **Как избежать.** Нужен кламп — делайте сами перед `set_value`. Подбирайте
  `increment` под `(max-min)` или используйте `cycle` (он перескакивает на
  ПРОТИВОПОЛОЖНУЮ границу, не на ближайшую). Для целого ввода форматируйте `:g` и
  приводите `int(counter.get_value())` в getter.
- **Главы:** 12 (§2.4, §5.2, §5.3, §5.4, §5.5).

### 9.3. `set_checked` — абсолютная установка, не toggle
- **Суть.** `ManagedCheckbox.set_checked(bool)` УСТАНАВЛИВАЕТ значение, не
  переключает (на реальном клике инверсия делается внутри `_process_item_callback`
  относительно отрисованной кнопки `"0"`/`"1"`). `Multiselect.reset_checked`
  сбрасывает в `[]` ЖЁСТКО, игнорируя `min_selected` и НЕ вызывая `on_state_changed`.
  `Radio`/`Multiselect.set_checked` сравнивают по `str(item_id)`.
- **Чем грозит.** Ожидание toggle от `set_checked` даст не тот результат; логика на
  `on_state_changed` не сработает при `reset_checked`.
- **Как избежать.** Для инверсии: `await cb.set_checked(not cb.is_checked())`. Учтите,
  что `reset_checked` не триггерит `on_state_changed`.
- **Главы:** 11 (§5, §6, §11.5), 12 (§1.4, §5.7).

### 9.4. `type_factory` обязателен для не-str item_id; item_id всегда строка
- **Суть.** В `Select`/`Radio`/`Multiselect`/`Toggle` `item_id` в callback и в
  `widget_data` всегда строка (`str(...)`/f-string). `get_checked()` и аргумент
  `item_id` в `on_click`/`on_state_changed` приводятся обратно через `type_factory`
  (по умолчанию `str`). Сравнения `is_checked`/`set_checked` идут по строке.
- **Чем грозит.** Без `type_factory` получите строки вместо нужного типа (int,
  datetime); смешение `True`/`1` как ключей или `"42"`≠`42`.
- **Как избежать.** Задавайте `type_factory` (например `int`, кастомный парсер). Тип
  ключа в `Case`/селекторах должен совпадать с типом результата селектора.
- **Главы:** 08 (§6 Case), 11 (§2, §4, §11.1).

### 9.5. Прочие краевые случаи stateful-виджетов
- **Суть/как избежать.**
  - `Multiselect` помнит исчезнувшие из `items` id (удобно при пагинации, но
    `get_checked()` вернёт «осиротевшие» id — фильтруйте вручную, если данные реально
    удалены). `min_selected` не задаёт начальный выбор; `max_selected=0` = безлимит.
  - `Select` кладёт все кнопки в ОДИН ряд, `Toggle` — одна кнопка (меняет элемент по
    кругу, без «снятия»). Раскладку дают `Column`/`Row`/`Group`.
  - `on_click` у stateful-виджетов вызывается ДО смены состояния-эффекта, но получает
    уже типизированный `item_id` (`T`); «новое» состояние читайте в `on_state_changed`.
  - `Counter.on_click` срабатывает и на клике по центральной кнопке (значение НЕ
    меняется); для реакции на изменение используйте `on_value_changed`.
  - `manager.find(id)` возвращает managed-обёртку или `None` (если id нет в дереве);
    скрытый через `when` виджет всё равно есть в дереве и находится `find`.
  - `items` через строку → `itemgetter` → `KeyError` при отсутствии ключа; через
    `MagicFilter` → тихо `[]`, если результат не `Sequence` (строка тоже `Sequence` —
    разложится посимвольно). Возвращайте списки/кортежи, гарантируйте ключ в getter и
    `preview_data`.
- **Главы:** 11 (§3, §6, §11.6/11.7/11.8/11.10), 12 (§5.8/5.10).

### 9.6. Calendar/TimeSelect: специфика
- **Суть/как избежать.**
  - `Calendar.on_click` срабатывает ТОЛЬКО на выбор дня (не месяца/года); пустые
    кнопки имеют `callback_data=""` (клик игнорируется); `set_scope`/`set_offset` сами
    не перерисовывают.
  - `TimeSelect`: 2-й позиционный аргумент — `when`, НЕ колбэк (передавайте колбэки
    только по имени); `get_value`/`on_value_changed` вернут `None`, пока не выбраны
    оба компонента (час И минута).
- **Главы:** 13 (§3, §7.1/7.2, §9). (Про устаревший `custom.py` и tz-дефолт — см.
  тему 14.)

## Тема 10. getter и данные (порядок мерджа, системные ключи)

### 10.1. `KeyError` в `Format`/`List`/`DynamicMedia`/`Case` при отсутствии ключа
- **Суть.** `Format` использует `str.format_map(data)` — `{missing}` → `KeyError`,
  весь показ окна падает (нет «тихого» дефолта). `List(items="key")` и
  `Select(items="key")` используют `itemgetter` → `KeyError` без ключа (в отличие от
  `Case`/`Progress`, где `.get`). `DynamicMedia("key")` — тот же `KeyError`. `Case`
  без `...`-дефолта и без совпадения ключа → `KeyError` в проде.
- **Чем грозит.** Падение рендера окна на отсутствующем ключе данных.
- **Как избежать.** Гарантируйте наличие ключей в getter (и в `preview_data` для
  preview). Для опциональных полей: `when="key"` + fallback через `Or` (`|`),
  `Case(..., ...: default)`, `data.get(...)` в кастомных getter. `{`/`}` в `Format`
  экранируйте удвоением `{{`/`}}`.
- **Главы:** 08 (§3, §6, §8, §9), 11 (§3), 17 (§5).

### 10.2. getter не должен затирать системные ключи и обязан иметь `**kwargs`
- **Суть.** Базовый слой `manager.load_data()` кладёт `dialog_data`, `start_data`,
  `middleware_data`, `event`. Результат getter раскрывается ПОВЕРХ (`**data` идёт
  последним) → одноимённый ключ из getter ПЕРЕТРЁТ системный. Все getter вызываются с
  `**manager.middleware_data` — без `**kwargs` они упадут `TypeError` при появлении
  новых middleware-ключей.
- **Чем грозит.** Случайное затирание `event`/`dialog_data` ломает виджеты;
  отсутствие `**kwargs` → падение при добавлении DI.
- **Как избежать.** Не называйте поля getter `event`/`dialog_data`/`start_data`/
  `middleware_data`. Пишите `async def getter(dialog_manager, **kwargs) -> dict` и
  ВСЕГДА возвращайте `dict`.
- **Главы:** 02 (§2), 03 (§5, §9.10), 08 (§1), 19 (§9, §14.6/14.7).

### 10.3. Приоритет мерджа getter: window > dialog > global > системные
- **Суть.** `Window.getter` перекрывает `Dialog.getter`, тот — глобальный getter из
  `setup_dialogs(getter=...)`, и все они — системные ключи (поздний `update`
  побеждает). `getter=` принимает callable, dict (статика), list/tuple (мердж по
  порядку, поздний ключ побеждает) или `None`.
- **Чем грозит.** Неожиданное перекрытие данных при совпадении ключей на разных
  уровнях.
- **Как избежать.** Держите ключи уникальными между уровнями; используйте список
  getter осознанно (`getter=[a, b]` → `CompositeGetter`, мердж по порядку).
- **Главы:** 02 (§2 load_data), 03 (§5), 19 (§9).

### 10.4. Голый `Callable` в `*widgets` — это input-хендлер, не getter
- **Суть.** В `ensure_widgets` любой `Callable` среди позиционных виджетов трактуется
  как input → `MessageInput`. Getter передаётся ТОЛЬКО через `getter=`.
- **Чем грозит.** Функция, переданная позиционно как «getter», станет обработчиком
  сообщений.
- **Как избежать.** Getter — только `getter=...`. Параметры окна/диалога после
  `*widgets`/`*windows` — keyword-only (`state=` обязателен у `Window`).
- **Главы:** 03 (§1.2, §9.1, §9.2), 19 (§10).

### 10.5. `Window.find()` не ищет внутри `link_preview`
- **Суть.** `Window.find` сканирует `text/keyboard/on_message/media`, но НЕ
  `link_preview`.
- **Чем грозит.** id внутри `LinkPreview` недоступен через `manager.find()`.
- **Как избежать.** Не закладывайтесь на поиск виджетов внутри `LinkPreview`.
- **Главы:** 03 (§1.4, §9.9).

### 10.6. `manager.find` возвращает `None` при отсутствии id; используйте его, а не `widget.find`
- **Суть.** `manager.find(id)` оборачивает результат в `Managed*` (`widget.managed`);
  голый `widget.find()` — нет. Ищет по ВСЕМ окнам диалога. Возвращает `None`, если id
  нет.
- **Чем грозит.** `AttributeError`/неверное использование, если не проверить `None`
  или взять голый `widget.find`.
- **Как избежать.** Всегда `manager.find(id)` и проверка на `None`. Текстовые виджеты
  без id (`Const`/`Format`) найти нельзя.
- **Главы:** 12 (§5.8), 15 (§8.4), 19 (§6, §7, §14.1/14.3).

## Тема 11. Фон (BgManager, fg, updates)

### 11.1. `bg()` не валидирует адресацию — тихий промах
- **Суть.** `BgManager` не проверяет существование чата/стека до отправки апдейта.
  `handle_update` для `UPDATE` без контекста только пишет `logger.warning("No context
  found")` и выходит — ни исключения, ни сообщения. Для ЧУЖОГО чата `stack_id` по
  умолчанию становится `""` (DEFAULT_STACK_ID) — это ДРУГОЙ стек, чем у текущего юзера.
- **Чем грозит.** Неверная адресация = молчаливый промах (ничего не происходит, только
  warning в лог).
- **Как избежать.** Передавайте `stack_id` явно, если нужен конкретный стек.
  Проверяйте, что чат/юзер существуют. `manager.bg()` без аргументов = «тот же чат,
  стек, intent».
- **Главы:** 02 (§5), 06 (§3, §12).

### 11.2. Методы `BgManager` асинхронны (через `call_soon`) — гонки и flood-limit
- **Суть.** Методы `BgManager` возвращаются ДО реального выполнения (`Updater.notify`
  ставит задачу через `loop.call_soon` + `create_task`). Несколько подряд
  `bg.update()` из плотного цикла без `sleep` могут наложиться/перегнать друг друга и
  упереться в flood-limit Telegram при частых edit. `StartMode.NEW_STACK` тоже идёт
  через bg-очередь — не синхронно.
- **Чем грозит.** Гонки, flood-control, неожиданный порядок применения; нельзя ждать
  результат сразу после вызова.
- **Как избежать.** Дросселируйте частоту обновлений (как в примерах — `sleep(1)`).
  Помните: межапдейтные изменения `dialog_data` видны, только если сохранены
  предыдущим обработчиком.
- **Главы:** 02 (§3, §5, §10.5), 06 (§4, §5, §12).

### 11.3. `fg()` держит лок на стек — делайте тело короткое
- **Суть.** Пока вы внутри `async with bg.fg()`, обработчик «висит» на
  `await event.exited` — соответствующий стек ЗАБЛОКИРОВАН на вас.
- **Чем грозит.** Долгая работа внутри `with` блокирует другие апдейты этого
  пользователя/стека.
- **Как избежать.** Тело `with` — только мутация данных + `update()`; тяжёлую логику
  выносите наружу. `fg()` — единственный способ получить ПОЛНЫЙ `DialogManager` для
  чужого чата/фоновой задачи (у `ManagerImpl.fg` это просто `yield self`).
- **Главы:** 02 (§5), 06 (§6, §12).

### 11.4. bg-события НЕ проходят обычные middleware — вешайте на `DIALOG_EVENT_NAME`
- **Суть.** `BgManager` шлёт кастомные `aiogd_update`-события; ваши обычные
  aiogram-мидлвари (auth, throttling, i18n, БД-сессии) по умолчанию на них НЕ
  срабатывают. Внутренние мидлвари aiogram_dialog на `aiogd_update` уже навешаны.
- **Чем грозит.** Фоновый рендер диалога пойдёт БЕЗ вашей бизнес-middleware (например
  без локали → фолбэк-язык, без БД-сессии → ошибка).
- **Как избежать.** Регистрируйте нужные middleware на
  `dispatcher.observers[DIALOG_EVENT_NAME].middleware(...)`.
- **Главы:** 02 (§5, §10.8), 04 (§14), 06 (§5, §12).

### 11.5. `load=True` стоит запросов и может падать
- **Суть.** `BgManager` по умолчанию оперирует `FakeChat(type="")`/`FakeUser`. `_load`
  при `load=True` делает до 2 вызовов API (`get_chat`, `get_chat_member`). Без
  `load=True` fake-чат имеет `type=""` ≠ PRIVATE → AUTO в фоне почти всегда `EDIT`.
- **Чем грозит.** В вебхуках/брокерах — лишняя задержка и точка отказа (бот может не
  видеть чат/участника); без `load=True` неверная AUTO-логика SEND/EDIT по типу чата;
  при bg `from_user` может содержать только `id` (i18n по `language_code` упадёт в
  default).
- **Как избежать.** `load=True` включайте только когда геттеры/виджеты читают данные
  пользователя/чата или важна AUTO-логика по типу чата. Иначе задавайте `show_mode`
  явно.
- **Главы:** 06 (§7, §12), 20 (§4 i18n, §7 FAQ).

### 11.6. `SubManager.dialog_data` ≠ общий `dialog_data` диалога
- **Суть.** Внутри `ListGroup` менеджер — `SubManager`, у которого `dialog_data`/
  `current_context()` подменены на `widget_data[widget_id][item_id]` строки, а НЕ на
  общий `dialog_data` диалога. `manager.item_id` = id кликнутой строки.
- **Чем грозит.** Запись в `manager.dialog_data` внутри строки уйдёт в data строки, не
  в общий контекст.
- **Как избежать.** Для общего `dialog_data` используйте `manager.find_in_parent(...)`
  или родительский менеджер. `find` внутри строки ищет в строке, `find_in_parent` —
  снаружи.
- **Главы:** 02 (§7, §8, §10.9), 15 (§5.4).

## Тема 12. Текстовые виджеты (Format, Jinja, ScrollingText, List, Progress)

### 12.1. `ScrollingText(page_size=0)` → `ZeroDivisionError`; `ScrollingGroup(height=0)` тоже
- **Суть.** `ScrollingText.page_size` по умолчанию `0` → деление `len(text)//0` →
  `ZeroDivisionError`. Аналогично `ScrollingGroup.height` по умолчанию `0` →
  `_get_page_count` делит на `height`.
- **Чем грозит.** Падение рендера при дефолтных значениях (параметр не помечен
  обязательным, легко пропустить).
- **Как избежать.** Всегда задавайте `page_size > 0` (`ScrollingText`) и `height > 0`
  (`ScrollingGroup`).
- **Главы:** 08 (§10), 15 (§2.1, §8.1).

### 12.2. `ScrollingText` режет по символам — рвёт слова и HTML-теги
- **Суть.** Режет полную строку на куски по `page_size` СИМВОЛОВ
  (`text[offset:offset+page_size]`), не по словам/строкам.
- **Чем грозит.** При `parse_mode="HTML"` тег может «разрезаться» между страницами →
  ошибка Telegram. Не учитывает лимит 4096 символов сам по себе.
- **Как избежать.** Выставляйте `page_size` ≤ безопасного лимита; для HTML следите,
  чтобы теги не попадали на границу страниц (или избегайте сложной разметки в
  ScrollingText).
- **Главы:** 08 (§10).

### 12.3. `Progress`: `percent=None` → `TypeError`, не клампится
- **Суть.** `Progress` берёт `data.get(field)` → `None`, если ключа нет, и арифметика
  `width*None/100` падает `TypeError`. Значение не клампится: `>100` даёт
  переполненный бар, `<0` — некорректный.
- **Чем грозит.** Падение рендера/кривой бар.
- **Как избежать.** Гарантируйте наличие поля (getter отдаёт `0` по умолчанию:
  `dialog_data.get("progress", 0)`). Клампите значение сами при необходимости.
- **Главы:** 08 (§9).

### 12.4. `Jinja`: нужен `parse_mode="HTML"`, autoescape по умолчанию `True`
- **Суть.** `Jinja` — это HTML-рендер. Окружение по умолчанию `autoescape=True`
  (экранирует ПОДСТАВЛЯЕМЫЕ значения, не статику шаблона), `trim_blocks=True`,
  `lstrip_blocks=True`. `setup_jinja` для кастомных фильтров вешайте на `Dispatcher`
  (`dp[...]`), а не на `Bot` (на Bot → `DeprecationWarning`).
- **Чем грозит.** Без `parse_mode="HTML"` (на Window или глобально у бота) HTML-теги
  уйдут как текст. Кастомные фильтры без `setup_jinja(dp, ...)` не зарегистрируются
  (общий `default_env` их не знает).
- **Как избежать.** Ставьте `Window(parse_mode="HTML")` (или глобальный default).
  Подставляемый HTML из данных — через `|safe` (понимая риски). Литеральные `{{`/`}}`
  экранируйте по правилам Jinja.
- **Главы:** 08 (§7).

### 12.5. `Format`/`Multi`/`Const` нюансы
- **Суть/как избежать.**
  - `Const` НЕ интерпретирует `{}` — `{name}` в `Const` останется литералом
    (подстановка только в `Format`/`Jinja`).
  - `Multi` через `filter(None, ...)` отбрасывает пустые строки (скрытые `when=False`
    элементы не оставляют лишних разделителей) — это удобно, но учитывайте при
    подсчёте.
  - `parse_mode` окна по умолчанию `UNSET_PARSE_MODE` = «брать из `Bot.default`»;
    явный `None` отключает форматирование для окна.
  - `disable_web_page_preview` устарел: даже `False` создаёт
    `LinkPreview(is_disabled=True)` + `DeprecationWarning`; конфликт с виджетом
    `LinkPreview` → `ValueError`. Используйте виджет `LinkPreview`.
  - `List`: внутри шаблона элемента доступ к внешним данным через `data` (`{data[...]}`),
    `item`/`pos`/`pos0` — поля строки; `page_size` без `id` пагинацию не сохранит.
- **Главы:** 02 (§2), 03 (§9.4, §9.5), 08 (§2, §4, §8), 17 (§7 deprecated).

## Тема 13. Инструменты и окружение (render_transitions, preview, setup_dialogs)

### 13.1. `render_transitions` импортирует `diagrams` на уровне модуля + требует graphviz
- **Суть.** `tools/transitions.py` импортирует `diagrams` на уровне модуля и требует
  системный graphviz. Если их нет — сам `import` падает.
- **Чем грозит.** Если вызвать `render_transitions` в рантайме бота (или импортировать
  модуль на старте), прод упадёт без dev-зависимостей.
- **Как избежать.** Вызывайте только как dev-скрипт, не на старте бота (в примерах —
  ДО `start_polling`). Ставьте `aiogram_dialog[tools]` (`diagrams`, `aiohttp`) +
  graphviz только в dev. `render_transitions` не анализирует код callback'ов — ручные
  переходы (`manager.next()` в `MessageInput`) на графе не видны; подсказывайте через
  `Window(preview_add_transitions=[...])`.
- **Главы:** 05 (§9, §12.8), 20 (§2.1, §2.4).

### 13.2. `preview` (`render_preview`/web-preview) требует `aiohttp` и `preview_data`
- **Суть.** `render_preview`/web-preview требуют `aiogram_dialog[tools]` (`aiohttp`).
  `FakeManager.load_data()` возвращает `{}` — без `preview_data` у окон тексты с
  подстановкой ключей не отрендерятся (KeyError/плейсхолдеры).
- **Чем грозит.** Падение/пустой preview без extras и без `preview_data`.
- **Как избежать.** Ставьте extras; задавайте `Window(preview_data=...)`. Web-preview
  — порт 9876, рендер в отдельном процессе.
- **Главы:** 20 (§2.2, §2.3).

### 13.3. `setup_dialogs` — строго после `include_router`, один раз, на корневом роутере
- **Суть.** `setup_dialogs` навешивает middleware на УЖЕ собранное дерево роутеров и
  регистрирует core-handler. Параметры (кроме `router`) keyword-only. Если передать
  свой `dialog_manager_factory`, то `message_manager`/`media_id_storage`/`getter`
  ИГНОРИРУЮТСЯ. Побочно подключается встроенный `about_dialog` (лишняя группа
  `AiogramDialogStates.ABOUT`).
- **Чем грозит.** Диалоги, не включённые в дерево этого роутера, → `UnregisteredDialogError`
  при старте. Позиционная передача диалогов (старое API `*favourite_dialogs`) →
  `TypeError`. Свой factory молча отключает три параметра.
- **Как избежать.** Порядок: `Router` для диалогов → `include_router` → `setup_dialogs`
  ПОСЛЕДНИМ, на корневом роутере (`Dispatcher`). Диалоги регистрируйте через
  `include_router`, не позиционно. Свою фабрику прокидывайте `message_manager`/
  `media_id_storage`/`getter` внутрь сами. `Dialog.include_router` запрещён
  (`TypeError`) — вложенные диалоги делаются через `Start`/`manager.start`. Учитывайте
  About-диалог при аудите `collect_dialogs`/`render_transitions`.
- **Главы:** 01 (§1, §2, §3, §10.1/10.2/10.3/10.5/10.6), 03 (§2.3), 07 (§6), 20 (§3, §5).

### 13.4. i18n: middleware на `message` И `callback_query`, без кеша текста
- **Суть.** В примере i18n локаль кладётся в `data[I18N_FORMAT_KEY]` middleware;
  `I18NFormat` хранит КЛЮЧ перевода и рендерится на каждый показ. Middleware надо
  вешать и на `dp.message`, и на `dp.callback_query`.
- **Чем грозит.** Если middleware только на `message`, при нажатии кнопки локаль не
  подставится → фолбэк-язык. Свой кеш текста в виджете сломает переключение языка.
- **Как избежать.** Вешайте локаль-middleware на оба типа событий (и на
  `DIALOG_EVENT_NAME` для bg, см. 11.4). Не кешируйте перевод в виджете.
- **Главы:** 20 (§4).

### 13.5. Тест-инструменты: нюансы
- **Суть/как избежать.**
  - Нужен `storage` у `Dispatcher` (FSM). Для тестов — `JsonMemoryStorage` (ловит
    несериализуемые данные через `json.dumps`).
  - `MockMessageManager.one_message()` падает при 0 или >1 сообщений — между шагами
    `reset_history()`.
  - Локаторы кнопок (`InlineButtonTextLocator`/`DataLocator`) используют `fullmatch`,
    не `search`: `"Next"` не найдёт `"➡️ Next"` — используйте `".*Next.*"` или
    `InlineButtonDataLocator`. Локаторы работают только по inline-клавиатуре.
  - `SimpleEventIsolation` подключается автоматически даже в тестах (два одновременных
    `/start` — строго по одному).
- **Главы:** 20 (§1.3, §1.4, §1.5, §1.6).

## Тема 14. Известные баги и неточности в коде/доках текущего коммита

### 14.1. Текст ошибки EXCLUSIVE врёт про SINGLE
- **Суть.** При старте поверх `LaunchMode.EXCLUSIVE` бросается
  `ValueError("Cannot start dialog on top of one with launch_mode==SINGLE")`, хотя
  проверяется `EXCLUSIVE` — историческая неточность сообщения (логика верна, текст
  вводит в заблуждение).
- **Чем грозит.** Отладка по тексту ошибки сбивает с толку (ищешь SINGLE, а проблема в
  EXCLUSIVE).
- **Как избежать.** Помните: «SINGLE» в этом сообщении = `EXCLUSIVE`. См. 1.4.
- **Главы:** 02 (§3), 03 (§3), 05 (§2 note), 10 (§7).

### 14.2. Устаревший `docs/.../calendar/custom.py`
- **Суть.** `custom.py` (и старые примеры) передают `self.config` ВТОРЫМ позиционным
  во view (`CalendarDaysView(self._item_callback_data, self.config, ...)`), но в
  текущем коде второй позиционный — это `date_text: TextWidget`, а `config` view не
  принимает (получает в `render()`). Передача `CalendarConfig` туда, где ждут `Text`,
  ломает рендер.
- **Чем грозит.** Копирование `custom.py` уронит/сломает рендер календаря.
- **Как избежать.** Ориентируйтесь на mega-пример (`calendar.py`) — там только
  `self._item_callback_data` без `self.config`.
- **Главы:** 13 (§вступление, §9).

### 14.3. `CalendarConfig.timezone` вычисляется один раз на импорте модуля
- **Суть.** Дефолт `timezone = datetime.now().astimezone().tzinfo` — это значение поля
  по умолчанию, зафиксированное при ИМПОРТЕ модуля. В долгоживущем процессе при смене
  летнего/зимнего времени не обновится. tz влияет только на подсветку «today», на
  выбранную (naive) дату — нет.
- **Чем грозит.** На сервере «сегодня» может подсветиться неверно после смены
  DST/часового пояса процесса.
- **Как избежать.** Для серверов задавайте `timezone` явно (`timezone.utc` или нужная
  зона) в `CalendarConfig`. Не путайте tz календаря с tz пользователя для бизнес-логики.
- **Главы:** 13 (§2.1, §9).

### 14.4. Устаревшие/отсутствующие API из старых версий (не закладывайтесь)
- **Суть.** В текущем коммите ОТСУТСТВУЮТ упоминавшиеся в разных источниках сущности:
  - `setup_dialogs(dp, *favourite_dialogs, registry=...)` — нет `*favourite_dialogs`
    и `registry`; `DialogRegistry` внутренний, не экспортируется.
  - `TextUnchangedFilter`, `int_factory`/`float_factory` — нет (type_factory это
    обычный `Callable[[str], T]`).
  - `GeneratorType`/`register_callback` в `widget_event.py` — нет (нормализация только
    через `SimpleEventProcessor`; несколько обработчиков — своим подклассом
    `WidgetEventProcessor`).
  - `Or` (text) НЕ экспортируется (только через оператор `|`).
  - `Case` лежит в `widgets/text/multi.py`, НЕ в `case.py` (файла `case.py` в
    `widgets/text/` нет).
  - `dialog_manager.data` устарел → актуально `dialog_manager.middleware_data` (в
    `faq.rst` ещё встречается старое имя).
  - Managed-обёртки переименованы (`...Adapter` → `Managed...`), `Registry` удалён,
    каждый `Dialog` теперь `Router`.
- **Чем грозит.** Копирование примеров из старых версий/туториалов → `TypeError`/
  `ImportError`/`AttributeError`.
- **Как избежать.** Ориентируйтесь на текущий код (develop `08abdf0`) и mega-пример;
  сверяйтесь с `docs/migration.rst`.
- **Главы:** 01 (§2 note, §9), 08 (§вступление, §5, §6), 16 (§вступление), 19
  (§вступление, §14.10), 20 (§7 note, §8).

### 14.5. Мелкие неточности кода/доков
- **Суть/как избежать.**
  - `_handle`/`edit_caption` путь «тот же файл → edit_caption» в `MessageManager`
    фактически почти не срабатывает (сравнение `MediaId` со `str` даёт `False`) —
    учитывайте при отладке «мигающего» медиа.
  - Опечатка в имени параметра `sync_scroll(on_page_chaged=...)` (без `n`) — при
    передаче по имени используйте именно это написание.
  - `time/index.rst`: параметр Protocol назван `counter` (копипаст из Counter) — на
    поведение не влияет.
  - В сниппете `docs/.../render_preview.py` опечатка
    (`await render_transitions(dp, "preview.html")`) — правильно `render_preview`.
  - `Back` имеет рудиментарную строку `self.callback_data = id`, на маршрутизацию не
    влияет.
  - `years_per_page` не строго кратно `years_columns` → последняя строка лет может
    содержать лишние года; берите кратные значения (дефолт 20/5 кратен).
- **Главы:** 07 (§3.5), 10 (§2.3), 13 (§7.2, §9), 15 (§1.4), 20 (§2.4).
